次に実装すべき作業を、**思い込みではなく実地調査**で決めてください。
対象候補のヒント: $ARGUMENTS(未指定なら以下の定型で棚卸し)。

## 手順

1. **候補の列挙**(3〜5 件に絞る):
   - 最新の `docs/development/session-handoff-*.md` §残件
   - open issues(`lane:*` label つき。`frozen` は候補にしない)
   - **直近 merge した PR が設計 doc / §1 調査で挙げた未修正 gap**
     (「別 PR で」「据え置き」と書いて着地させたもの — 忘れられやすい)
2. **並列調査**: 候補ごとに `pkc2-surveyor` subagent を並列起動し、
   現状・実装量(S/M/L)・リスク・blockers を file:line 根拠つきで集める。
   調査 prompt には必ず「直近 main の変更で前提が変わっていないか検証せよ」を
   含める(例: 見送りの根拠が事実と違っていた ZIP ゲート、DOM 変更で静かに
   壊れた copy)
3. **回帰の疑いを先に潰す**: 直近 PR が DOM 形状・データ形式・selector 契約を
   変えていたら、その**消費者**(`:scope >` selector / copy / minimap /
   split-sync / export 等)への影響を候補調査と同時に確認する。回帰が
   見つかったらそれが最優先
4. **比較と推薦**: 表(候補 × 実装量 / リスク / 根拠)+ 推薦 1 つを会話で提示。
   **user 判断待ちとされている項目は、調査結果の提示までに留めて着工しない**
   (裁定が出たら doc-first で進める)

## 注意

- 調査は read-only。この command の中で実装を始めない
- 候補が実は完了済み(例: R15 がマニュアル掲載済みだった)というケースが
  実際にあるので、「未着手のはず」も検証対象にする
