---
description: 性能の主張を「後から覆されない数字」にする(手法検証 → 対照群 → fixture → 測定 → 限界の明記)
---

測る対象: $ARGUMENTS(未指定なら会話の文脈から 1 文で定義してから始める)

**`perf-measurement` スキルを読んでから始めてください。** 以下はその実行手順です。
数字を出す前に 1〜4 を必ず通すこと ── 2026-07 に同一セッションで 6 回計測を誤り、
6 回とも「もっともらしい数字が出てから」誤りに気づいた。

## 手順

1. **問いを 1 文にする** ── 「〈どの操作〉の〈どの指標〉が〈どの規模〉で〈どれだけ〉違うか」。
   書けないなら測る段階ではない。ここで止めて user に確認する

2. **計器が反応することを先に確かめる** ── 既知の入力を 2 水準以上入れて線形応答を見る。
   **ノイズ床**(何もしないときの値)を取り、信号がその 10 倍以上あることを確認。
   非同期の値は**実体化した後**に区間を閉じる(`req.result` 参照前に閉じて
   structured clone のコストを取り逃した前科あり)

3. **対照群を定義する** ── 「何もしない」は対照群ではない。
   **測りたい操作以外を全部同じにした腕**を作る(PKC2 なら `CANCEL_EDIT` が
   `SAVE_TRIGGERS` に無いことを使える)。
   **検算**: 入力規模を 1/10 にして対照群の値が変わらないこと。変わるなら対照群が汚れている

4. **fixture の各次元の件数を印字する** ── entries / revisions / relations / assets。
   **0 の次元があれば、0 のまま測ってよい理由を言えること**。
   言えないなら `build/scripts/generate-bench-container.ts --revisions=<N>` 等で作り直す。
   (`bench-fixtures/c-*.json` が revisions 0 件だったせいで、歴代のベンチが全部
   「無料の道」しか通っておらず、boot の 65% を占める O(N×M) を誰も見つけられなかった)

5. **測る** ── ハーネスは `perf-measurement` スキルの使い分け表から選ぶ。
   まず `npm run bench:write-volume`(アプリが書けと言った量。ブラウザの
   オーバーヘッドが入らない)、実コストが要るなら `npm run bench:write-io`。
   履歴入り fixture は `npm run bench:fixtures:rev` で生成する。
   ⚠ **実行中に `npm run build:bundle` / `build:release` を回さない**(dist が消えて落ちる)

6. **反復する** ── 最低 3 回。中央値とレンジを出す。
   **ハーネスに無効判定を埋める**(差し引きが負 / 対照群が実測値を上回る →
   `⛔ この実行の数字を結論に使ってはならない` を印字)

7. **推定した機構は直接観測してから実装に進む** ── 「たぶん UI 設定の保存だろう」で
   実装しない。それを切り分ける腕を足して測る

8. **doc にする** ── `docs/development/<主題>-YYYY-MM-DD.md`、同 commit で INDEX 登録。
   - 先頭に測定条件(fixture の各次元 / 反復 / 腕 / 対照群の定義)
   - **指標ごとの信頼度表**(直接測定 = 固い / 差し引き = 向きのみ)
   - **限界を明記する節を必ず置く**(測れなかったもの・条件に敏感なもの・未実施の再測)
   - 百分率は「**どの実行の、何に対する比率か**」まで書く。
     改善後に再掲するときは取り直す(修正前の比率を流用しない)

9. **自分の過去の数字を訂正するときは、訂正と明示して残す**。消さない

## やってはいけないこと

- 手法が固まる前に数字を会話に出す
- 「何もしない」を対照群と呼ぶ
- 差し引きで出た倍率を断定的に書く(向きだけにする)
- `(program)` のような受け皿バケットを「バンドルのパース」等と断定する
- 限界の節を省く
