# セッション引き継ぎ

> **user 指示(2026-07-26)**:
> 「**セッション引き継ぎはセッション引き継ぎ用の PR を作成して、その PR を渡すことで
> セッション引き継ぎを完成させます。PR には引き継ぎ事項のほかに最初の仕事の有無を
> 含めてください**」

## 0. 何をもって「完成」とするか

**PR を作り、その URL を user に渡した時点で完成。** doc を書いただけ、会話に要約を
書いただけでは完成していない。

理由: 次のセッションは会話履歴を持たない。**PR という 1 個の URL に集約されている**
ことが、引き継ぎが機能する条件である。

## 1. 🔴 最初の仕事の有無 ── 必ず書く

PR 本文の**冒頭**に、次の 3 択のどれかを明記する。

| 区分 | 書き方 |
|---|---|
| **あり** | 「**最初の仕事: あり**」+ 何を・どこから・完了条件。次セッションは確認せず着手してよい |
| **なし(指示待ち)** | 「**最初の仕事: なし。user の指示を待つ**」 |
| **user 裁定待ち** | 「**最初の仕事: なし。user の裁定待ちの案件が N 件ある**」+ 何を裁定してほしいか。**催促はしない** |

⚠ **ここを曖昧にしない。** 「あとは適当に続けて」は最悪で、次のセッションが
**勝手に仕事を作る**。「なし」と書くことは手抜きではなく、**それ自体が指示**である。

## 2. PR に入れるもの

### (a) 現在の状態(次セッションが最初に確認する事実)

```
main の HEAD    : <hash> <title>
open PR         : 無し / #NNNN(状態)
予約(send_later): 無し / 何の予約が何時に
作業 branch     : claude/<name>(main から作り直し済みか)
```

### (b) 着地したもの(1 行ずつ・数字つき)

PR 番号 + 何を + **実測値**。「改善した」ではなく「749 → 531 ms」と書く。

### (c) 🔴 やらないと決めたこと **と、その理由**

引き継ぎで**最も価値が高い**のはここ。次のセッションが同じ案を再発明して、
同じ調査をやり直すのを防ぐ。

```
❌ core record 丸ごと gzip     → サイズ 7.2 倍だが CPU 1,193 ms/編集(実測)
❌ revision の snapshot 分離   → 66.7% に見えて実際に買えるのは 20 ms(実測)
❌ 差分保存の既定 ON           → boot が 5.5 倍(同条件 2 回で再現)
```

### (d) 未測定・未確定の区別

「測って効かないと分かった」と「まだ測っていない」を**混ぜない**。
前者は結論、後者は宿題。

### (e) user 裁定の記録(出典タグ付き = 不可侵)

`(user 指示/裁定 YYYY-MM-DD)` を付けて再掲する。次セッションはこれを勝手に変えない。

### (f) 踏んだ罠 → **資産化したか**

罠は `.claude` へ反映済みのはず(`.claude更新`)。**どこに書いたかを指す**。
PR 本文で罠を再説明しない ── 資産が正本で、PR はポインタ。

## 3. 手順

```bash
# 1. 状態を確定させる(open PR / 予約を残さない)
git fetch --prune origin main
git log --oneline origin/main -5
#    open PR があるなら着地させるか、引き継ぎ事項として明記する
#    send_later の予約は削除する(次セッションに届いても文脈が無い)

# 2. doc を書く
#    docs/development/session-handoff-YYYY-MM-DD.md
#    同 commit で INDEX 登録
npm run check:doc-orphans

# 3. 引き継ぎ**専用**の PR を出す(実装と混ぜない)
#    PR 本文 = doc の要約ではなく、**それ単体で読める**こと
#    冒頭に「最初の仕事の有無」

# 4. user に PR URL を渡す ← ここで完成
```

## 4. 次セッションの入口(PR に必ず書く 1 節)

```markdown
## 次セッションへ

このセッションを引き継ぐには、新しいセッションの最初にこの PR の URL を渡してください。

1. まず「現在の状態」を `git fetch` で照合する(この PR を書いた後に main が
   動いている可能性がある)
2. 「最初の仕事」の区分に従う ── **なし** なら user の指示を待つ
3. `CLAUDE.md` と `.claude/skills/` を読む(規律はそちらが正本。本 PR は現況のみ)
```

## 5. 書かないもの

- **成功しただけの作業の詳細**(PR 番号と数字で足りる)
- **会話の経緯**(誰が何と言ったか。裁定だけ残す)
- **規律の再説明**(`.claude` が正本。重複させると乖離の元)
- **「たぶん」を断定で**(未確定は未確定と書く)

## 6. 自己点検

- [ ] **最初の仕事の有無**が冒頭にあるか(3 択のどれか)
- [ ] open PR / 予約 を残していないか(残すなら明記したか)
- [ ] 着地したものに **実測値**が入っているか
- [ ] **やらないと決めたこと**とその理由を書いたか
- [ ] 「測って否定した」と「未測定」を**分けて**書いたか
- [ ] user 裁定に**出典タグ**が付いているか
- [ ] 罠は `.claude` に反映済みで、PR は**ポインタ**になっているか
- [ ] PR 本文が **それ単体で読める**か(doc を開かないと分からない書き方をしていないか)
