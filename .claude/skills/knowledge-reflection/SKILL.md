# 知見を .claude へ反映する

> 「**着地後に知見を .claude に反映してくれ。コレは今度からスキルやコマンド、
> ルール、エージェントの更新に使用する言葉です**」(user 指示 2026-07-26)
>
> 「**コレ自体もスキル化しておいてください**」(user 指示 2026-07-26)── 本スキルがそれ。
>
> ⚠ この 2 行は出典タグ付き = **不可侵領域**。削除・希釈・言い換えによる骨抜きを禁ずる
> (CLAUDE.md「資産の自己免疫整備」)。

CLAUDE.md「資産の自己免疫整備」の実行手順。あの節が **方針**、本スキルが **手順**。

## 0. いつ走るか

- **着地後**(PR が merge され、main に入ってから)が既定。
  着地前は「結局どう直したか」が確定しておらず、書いた内容が嘘になる
- 例外: **その場で直せる実態との乖離**(廃止済み flag への言及、壊れた導線)は
  見つけた瞬間に直す。着地を待たない

## 1. 何を拾うか ── 4 種類だけ

セッションの出来事を全部書くのではない。**次に使う人の判断を変えるもの**だけ拾う。

| 種類 | 例(2026-07-26 の実例) |
|---|---|
| **踏んだ罠** | ハーネスの `⚠`/`⛔` を自分の grep で捨てた / `.gitignore` の漏れで 25MB を commit しかけた |
| **覆った前提** | 「保存が体感を殺している」→ 実測すると描画だった / 「静的分解で 7.2 倍」→ CPU を測ると 1 編集 1.2 秒 |
| **user 裁定** | lazy_entry_bodies の退役、3 ヶ月後廃止、導線封鎖と戻し道 |
| **実態との乖離** | doc に別ハーネスの数字が並んでいた / flag コメントの数字が条件付きだった |

**拾わないもの**: 一度きりの手順、そのセッション固有の事情、成功しただけの作業。

## 2. どこへ書くか ── 書き先の決め方

| 知見の性質 | 書き先 |
|---|---|
| ある作業の**やり方**が変わる | 該当スキル(`perf-measurement` / `merge-on-green` / …) |
| **どの作業でも**守るべき規律 | `CLAUDE.md`(節を増やさず既存節へ 1〜2 行) |
| **判断の記録**(なぜそう決めたか) | `docs/development/*.md` + INDEX 登録 |
| 特定の**調査の型** | 新しいスキル(既存に入らないときだけ) |

⚠ **迷ったら既存スキルへ足す。** 新スキルを作るのは「既存のどれにも属さない作業の型」が
できたときだけ。スキルが増えすぎると、次に使う人がどれを読むか分からなくなる。

## 3. 書き方 ── 3 つの型

### (a) 罠は「症状 → 原因 → 規律」で書く

```
🔴 ハーネスの無効判定を grep で捨てない(2026-07-26)
   症状: 「layout 5 が速くなった」と読める数字が出た
   原因: grep -E "^■|boot 中央値" で ⚠ 行ごと捨てていた。ハーネスは
         正しく「B と C の layout が同じ = flag が効いていない」と出していた
   規律: 出力を絞るときは必ず ⚠ と ⛔ を残す
```

**「気をつける」で終わらせない。** 次に同じ状況になったとき機械的に判定できる形にする。

### (b) 覆った前提は **両方**残す

古い数字を消すのではなく、**「こう見えたが、こう測ったらこうだった」**を残す。
消すと、次に同じ静的分解をした人がまた同じ判断をする。

### (c) user 裁定は出典タグ付きで、**不可侵領域**として書く

`(user 指示/裁定 YYYY-MM-DD)` を付ける。CLAUDE.md の規約どおり、
タグ付き記述は削除・希釈・言い換えによる骨抜きを禁ずる。

## 4. 手順

```bash
# 1. 着地を確認(main に入っているか)
git fetch --prune origin main && git log --oneline origin/main -5

# 2. 書き先を開いて、上の §1 で拾った知見を §3 の型で足す
#    - 既存の記述と矛盾していないか必ず読む(自分が今日書いた記述も含む)
#    - 実態と乖離した記述を見つけたら **その場で直す**

# 3. doc を新設したら同 commit で INDEX 登録
npm run check:doc-orphans

# 4. 反映だけの PR として出す(実装と混ぜない)
```

⚠ **実装 PR に混ぜない。** 反映は独立した PR にする。混ぜると
「実装をレビューしたいのに doc 差分が大半」になり、どちらも雑に読まれる。

## 5. 反映したかの自己点検

- [ ] 拾った知見が **§1 の 4 種類**のどれかに当てはまるか(当てはまらないなら書かない)
- [ ] 罠は **機械的に判定できる形**になっているか(「注意する」で終わっていないか)
- [ ] 覆った前提は **古い見立ても残して**いるか
- [ ] user 裁定に **出典タグ**が付いているか
- [ ] 新スキルを作ったなら、**既存スキルに入らない理由**を書いたか
- [ ] 実態と乖離した既存記述を **ついでに直した**か
