# 性能計測の規律

> **測り方が固まっていない数字を出すな。** 出した数字は必ず「どの実行の、何に対する
> 比率か」まで言えること。言えないなら、それはまだ測っていない。

2026-07 の storage 再設計調査で、**同じセッション中に 6 回**計測を間違えた。
6 回とも「もっともらしい数字が出てから」誤りに気づいた。
本スキルはその 6 つを二度と踏まないための手順である。

---

## 0. 使う前に ── 何を測るのか 1 文で書く

「A より B が速い」ではなく **「〈どの操作〉の〈どの指標〉が〈どの規模〉で〈どれだけ〉違うか」** まで書く。
書けないなら、まだ測る段階ではない。

例(良い): 「1 編集(本文 1 文字)で **IDB に put されるバイト数**が、
N=5000/M=15000 のコンテナで、差分保存 ON と OFF でどれだけ違うか」

---

## 1. 🔴 手法の実行可能性を先に確かめる(罠 ①)

**本番を測る前に、計器が反応することを確かめる。**

- 既知の入力を 2 水準以上入れて、**線形に応答するか**を見る
- **ノイズ床**(何もしないときの値)を必ず取る。信号がノイズ床の 10 倍以上あるか

> 実例: `/proc/diskstats` が使えるかを、本番の前に「20MB 書く / 60MB 書く / 何もしない」で確認した。
> ノイズ床 0.7MB に対し 19.3 / 54.4MB。**先に確認したから本番の数字を信用できた。**

計器そのものにも穴がある。**非同期の値は「実体化した後」に区間を閉じる**。

> 実例(罠 ①-b): IndexedDB の計測 span を `req.result` アクセス**前**に閉じていたため、
> structured clone の復元コストが丸ごと「その他」に流れ込み、
> **IDB が 0.2% と出た**(正しくは 1.5%)。

## 2. 🔴 対照群は「測りたい操作以外を全部同じにしたもの」(罠 ②)

**「何もしない」は対照群ではない。**

> 実例: 保存の書込量を測るのに「ブラウザ放置」を対照群にして
> **「1 編集あたり 3.2MB」**と出した。
> ところが **コンテナを 1/10(4.8MB → 500KB)にしても 4.1MB と出た** ──
> 測れていたのは保存ではなく **操作そのものがブラウザに書かせる分**だった。
>
> 対照群は **同じクリック・同じ打鍵・同じ画面遷移をして、測りたい操作だけが無い腕**。
> PKC2 では `CANCEL_EDIT` が `SAVE_TRIGGERS`(`persistence.ts:48-78`)に含まれず、
> reducer も `EDIT_CANCELLED` しか emit しない(`app-state.ts:4246-4255`)ので、
> 「編集して確定せず抜ける」が使える。

### ⚠ その対照群も汚れていた(2026-07-26 追記)

`storage-write-io.mjs` の対照群 Y は **1 反復が行クリック(= エントリ選択)から始まる**。
後の計測(`save-write-volume-2026-07-26.md` §(d))で **選択するだけでコンテナ全体が
書かれる**ことが判明したため、**Y は「保存が 1 回起きる腕」だった**。
A(編集)は 2 回なので、A − Y は「2 回 − 1 回 = 1 回分」を測っていたことになる。

⇒ **対照群は「測りたい操作以外を全部同じにする」だけでは足りない。
その「全部同じ」の中に測定対象が紛れていないかを、別の計器で確かめる。**
ここでは `bench:write-volume`(put を直接数える計器)が Y の汚染を暴いた。

### 対照群が正しいかの検算 ── 主語に注意

**入力規模を 1/10 にして、〈差し引き後の結論値〉が比例して縮むこと**を確認する。
縮まないなら、結論値は測定対象ではなく別の何かを測っている。

> ⚠ **「対照群の値が変わらないこと」を確かめても意味がない**(この検算を最初そう書いて誤った)。
> 誤った対照群だった Z(ブラウザ放置)の値は、コンテナを 1/10 にしても**変わらない** ──
> 放置中のブラウザ書込はコンテナ規模と無関係だからである。**Z はこの検算に合格してしまう。**
>
> 実際に失敗を暴いたのは **結論値**のほうだった:
> 「1 編集 3.2MB」がコンテナ 4.8MB → 500KB でも **4.1MB のまま**だった
> (`storage-write-io-bench-2026-07-25.md:47-49`)。
> **結論値がスケールしないなら、その計測は無効。**

## 3. 🔴 fixture が実ユーザーのデータと同じ形か(罠 ③ ── 最も高くついた)

> **2026-07-26 追記**: ゼロ件だった次元をもう 1 つ見つけた ── **削除済み entry**。
> 既存 fixture は 5 つとも削除済み lid が 0 件で、ゴミ箱ペイン
> (復元候補ごとに revision の `snapshot` を parse する)を**一度も測っていなかった**。
> `generate-bench-container.ts --deleted=<N>` を追加済み。
> 測った結果: 既定 boot は 414 → 416 ms で**効かない**と確定した。
> **「効かない」と分かること自体が成果**である ── 次の案のリスクが 1 つ減る。

> **ゼロ件の次元があるなら、それは「測っていない次元」である。**

> 実例: **commit 済の `bench-fixtures/c-*.json` 5 件**(c-100 / c-500 / c-1000 / c-5000 / c-audit)は
> **すべて revisions が 0 件**だった(`*-rev.json` は 2026-07-25 に追加した未 commit の生成物)。
> `getRevisionCount` には `revisions.length === 0` の早期 return があるため、
> **歴代のベンチが全部「無料の道」しか通っていなかった**
> (storage-backend-benchmark / differential-save-benchmark / 300MB の A.1 /
> lazy_entry_bodies の boot 測定)。
> 実ユーザーは編集のたびに履歴が増えるので必ずこの経路を踏む。
> 履歴入り fixture を作って初めて **boot の 65% を占める O(N×M)** が露出した。

**測る前に fixture の各次元の件数を印字する。** 0 の次元があれば、
それを 0 のまま測ってよい理由を言えること。

```bash
npm run bench:fixtures:rev        # 履歴入り fixture(1000/3000 と 5000/15000)を生成
# 任意の規模が要るとき:
npx tsx build/scripts/generate-bench-container.ts \
  --entries=15000 --textlogs=300 --assets=0 --revisions=45000 \
  --output=bench-fixtures/c-15000-rev.json   # --textlogs 省略時は既定 20 になる
```

`*-rev.json` は `.gitignore:14` 済み(seed 固定で決定的に再生成できるため commit しない)。

## 4. 🔴 推測した機構のまま実装しない(罠 ④)

原因の**機構を推定したら、それを直接観測する腕を足してから**実装する。

> 実例: 「1 編集で保存が 2 回走る」の 2 本目を「UI 設定の保存だろう」と推定した。
> 実装する前に **編集しない腕(選択だけ)** を足して測ったところ、
> **選択 1 回でコンテナ全体(5,104 KB)が書かれている**ことが確定した。
> 推定のまま実装していたら、別の場所を直していた可能性がある。

## 5. 🔴 指標ごとに信頼度を分けて書く(罠 ⑤)

| 測り方 | 信頼度 |
|---|---|
| **直接測定**(boot 所要 / storage 使用量 / put バイト数) | 🟢 固い |
| **差し引き**(腕 − 対照群) | 🟡 **向きのみ**。倍率は条件依存 |

> 実例: 同じ 5000 件でも編集回数を 6 → 4 に変えると、差し引き値が -26% → -63% に動いた。
> **向きは一貫していたが倍率は信頼できない。** doc にそう書いた。

**ハーネス自身に無効判定を埋める。** 差し引きが負になる・対照群が測定対象を上回る、
といった条件で `⛔ この実行の数字を結論に使ってはならない` を印字して止める。

> 実例: 15000 件で対照群が 41.1MB に膨れ、実測値(30.6 / 31.9MB)を上回った。
> ハーネスのガードが自動で無効化したので、**無効な数字を doc に載せずに済んだ**。

## 6. 🔴 百分率は「どの実行の、何に対する比率か」まで言う(罠 ⑥)

> 実例: 「boot 3.1 秒の 73% が `(program)`」と書いた。
> **73.3% はプロファイラ有効時の 5,291ms に対する比率**で、
> プロファイラ無効の 3,110ms のものではない。混ぜてはいけない。
>
> 同じ doc で「ストレージは 1.5%」も **修正前**の比率だった。
> 修正後は 9.7%(絶対値は 351→511ms で横ばい、全体が縮んだだけ)。
> **改善後に比率を再掲するときは必ず取り直す。**

`(program)` のような **受け皿バケット**を「バンドルのパース」等と断定しない。
プロファイラ自身のオーバーヘッドも入る。分解には別の計測(Performance timeline /
longtask attribution)が要る。

---

## 7. 🔴 「量が多い」と「体感が悪い」は**別の主張**(罠 ⑦、2026-07-26)

put 計器は「アプリが書けと言った量」を測る。**それは体感ではない。**

実例: 既定パスは 1 編集で **25,688 KB** 書いていた。これを削るために storage 形式の
変更を計画したが、**メインスレッドの停止**を直接測ると:

```
保存に帰せられるメインスレッド停止(確定 − 取消): -16 ms / 編集   ← 単発走行
```

IDB の書込はメインスレッド外なので、量が多くても体感には出ないことがある。
**逆に、同じ操作で 670 ms 固まっていた**(犯人は描画だった)。

⇒ **量の計器で出した数字を、そのまま体感の根拠にしない。**
   体感を語るなら long task か `Performance.getMetrics` を測る。

⚠ ただしこの −16 ms は **単発走行の noise だった**(罠 ⑧)。同一走行で交互に測ると
   保存は 153〜381 ms を食っていた。**両方の罠を同時に踏むと結論が二重に狂う。**

---

## 8. 🔴 単発走行で結論を出さない ── 腕は**同一走行で交互に**測る(罠 ⑧、2026-07-26)

「A を測る → コードを変える → A を測る」は、走行間の状態差が丸ごと差分に乗る。
実際に同じ日のうちに **−16 ms → 238 ms → 180 ms → 381 ms** と揺れた。

**規律:**
- 比較する腕は **1 回の走行の中で交互に**回す(A→B→A→B)
- それができない指標は **最低 2 回**取り、**両方の値を書く**(片方だけ書かない)
- 走行をまたいだ絶対値は比較しない ── **同一走行内の腕どうしの差だけ**を使う

---

## 9. 🔴 内訳は `Performance.getMetrics` で割る ── CPU プロファイルの `(program)` では判定できない(罠 ⑨、2026-07-26)

V8 CPU プロファイルの `(program)` は**受け皿バケット**で、レイアウトも paint も
**プロファイラ自身のオーバーヘッドも**入る。ここが 30% あっても
「レイアウトが重い」とは言えない(本 skill §6 の再演になる)。

CDP の `Performance.getMetrics` は **ScriptDuration / LayoutDuration /
RecalcStyleDuration / TaskDuration** を直接返す。操作の前後で差を取れば割れる。

実例(N=5000、1 編集):

```
段階                     Script  Layout  Style   Task 合計
取消(保存なし)            89 ms   25 ms   62 ms    368 ms
確定(保存あり)           195 ms   37 ms   73 ms    749 ms
```

⇒ Layout / Style は支配的でない = **仮想化の領域ではない**。
   Script の差 106 ms が行の作り直し = **memo の invalidation を細かくする領域**。

この 1 枚で「どこを直すか」が決まった。**内訳を割る前に実装を始めない。**

## 10. 🔴 静的分解だけで案を採用しない ── **代金も測る**(罠 ⑩、2026-07-26)

「core record を丸ごと gzip すれば 25,668 → 3,578 KB(**7.2 倍**)」──
静的分解では最有力に見えた。**CPU を測っていなかった:**

```
gzip    1,193 ms / 編集   ← 追加で払う分
gunzip    105 ms / boot
(現行が払っている JSON.stringify 53 ms / JSON.parse 60 ms)
```

保存は debounce 300ms の裏で走る。**1 編集ごとに 1.2 秒メインスレッドを塞ぐ**ので、
書込が 7.2 倍減っても体感は確実に悪化する。⇒ 棄却。

同じ日に **もう 1 件**同型の棄却をしている: revision の `snapshot` 分離は
「core record の 66.7%」で最有力に見えたが、**実際に買えるのは
structured clone の 74 → 54 ms = 20 ms** だけだった(残りは IDB の
`put` / `applyBatch` 自体のコスト)。

⇒ **「削減できるバイト数」は案の採否を決めない。** その形式で**追加で払う代金**
   (CPU / boot / 番兵の新設 / 移行リスク)を同じ精度で測ってから並べる。

## 11. 🔴 ハーネスの無効判定を grep で捨てない(罠 ⑪、2026-07-26)

ハーネスには「この実行の数字は使えない」を自分で言わせる仕掛けを入れてある
(`storage-write-io.mjs` の対照群 Y 比較・B/C の layout 一致判定、
`save-write-volume.mjs` の put 0 判定、`storage-footprint.mjs` の基準ゼロ判定)。

**その出力を `grep` で絞ると、警告ごと捨ててしまう。**

実例(2026-07-26): `grep -E "^■|boot 中央値"` で腕と boot だけ拾ったところ、
`persistence.lazy_entry_bodies` の退役(#1027)で C 腕が layout 5 にならず
**B と同じ split v1 を 2 回測っていた**のに、ハーネスが出していた
`⚠ B と C の layout が同じ — flag が効いていない。計測が無効` を
自分の grep で消していた。危うく「layout 5 が速くなった」と誤読するところだった。

**規律:**
- 出力を絞るときは **必ず `⚠` と `⛔` を残す**
  `grep -E "^■|boot 中央値|⚠|⛔"`
- 数字を doc / PR に書く前に、**その実行の生出力を一度は最後まで見る**
- 「腕が意図した形式で走ったか」は数字より先に確認する項目である
  (flag の退役・既定変更・URL flag の無視などで、腕は**黙って別物になる**)

## 既存ハーネスの使い分け

> **2026-07-26 追加**(いずれも npm script 登録済み):
> - `bench:footprint`(`storage-footprint.mjs`)── **生存 record を全件読み戻して**
>   バイト数を積む。`navigator.storage.estimate()` は **IDB 自身の未回収領域を含む**
>   ので、「アプリが溜めているのか GC が遅れているだけか」はこれでしか分けられない
> - `bench:gzip-cost`(`gzip-core-record-cost.mjs`)── 圧縮案の **CPU の代金**
>   (round-trip 一致を検査してから数字を出す)
> - `bench:edit-block`(`edit-main-thread-block.mjs`)── 1 操作の **メインスレッド停止**
>   (long task)。対照 Y は同操作を `CANCEL_EDIT` で抜ける
> - `bench:sidebar-reuse-check`(`sidebar-reuse-dom-check.mjs`)── 描画最適化が
>   **DOM を壊していないか**の実ブラウザ確認

| 何を知りたいか | ハーネス | 特徴 |
|---|---|---|
| **保存 1 回でアプリが何を書けと言ったか**(項の同定・O(N+M) の検証) | `npm run bench:write-volume` | `IDBObjectStore.put` を包んで key ごとのバイト数。**ブラウザのオーバーヘッドが 1 バイトも入らない**。保存を測るならまずこれ。⚠ **⛔ 無効判定も対照群の腕も持たない**(持つのは write-io 側)ので、判定は自分で書く |
| **実際に何バイトディスクへ落ちたか** | `npm run bench:write-io` | `/proc/diskstats`。⚠ **Linux かつデバイス名が `vda` 限定**(`storage-write-io.mjs:98` でハードコード。nvme0n1 / sda のホストでは即 throw)。実コストだが対照群の差し引きが要る |
| **boot の時間がどこに消えているか** | **① まず既存の `npm run bench`** → `tests/bench/profile.bench.ts` + `src/runtime/profile.ts`(`?profile=1` で起動、結果は `bench-results/SUMMARY.md`) | ⚠ **自作する前に `profile.bench.ts:4-23` を読む。** リポジトリは既に seed/boot の race を踏んでおり(**空 IDB の boot を測ってしまう**)、two-phase boot(空 boot → seed → reload した方を測る)で対策済み。同じ穴を掘り直さない |
| 同上・**関数別 self-time が要るとき** | CDP Profiler を自作(`Profiler.start/stop` + self-time 集計) | **commit されたハーネスは無い**。作るなら minify 名はバンドルを grep して引き当て、必ず §1-b の**閉じの検算**を通してから数字を出す |
| **ストレージ方式そのものの比較**(IDB/OPFS/FSA/SQLite WASM) | `tests/bench/storage-arch-bench/` | 300MB 級。**persistent プロファイル必須**(ephemeral はメモリバックで実 I/O を踏まない) |
| **画面が本当にそう見えるか** | `visual-parity` / `shinsatsu` スキル | 本スキルの対象外(数値ではなく視覚) |

### 走らせる前に(preflight)

```bash
npm run build                 # 両ハーネスとも dist/pkc2.html を配信して測る
npm run bench:fixtures:rev    # *-rev.json は .gitignore 済み。clean clone では必ず要る
```

つまみ: `SWV_FIXTURE` / `SWV_EDITS`(既定 3)、`WIO_FIXTURE` / `WIO_EDITS`(既定 20)/ `WIO_BOOTS`(既定 5)。
**`*_EDITS` を変えると差し引き値の倍率が動く**(§5)ので、比較する実行では固定する。

**反復は同じコマンドを 3 回叩いて手で並べる。** どちらのハーネスも 1 起動では反復しない
(`WIO_BOOTS` は boot 時間の反復であって書込量の反復ではない)。

⚠ **ベンチ実行中に `npm run build:bundle` / `build:release` を回さない。**
vite が `dist/` を作り直すので走行中のブラウザが落ちる(実際に踏んだ)。

## 出力の作法

1. **doc にする**(`docs/development/*-YYYY-MM-DD.md`)。同 commit で INDEX 登録
2. **測定条件を先頭に**: fixture の各次元の件数 / 反復回数 / 腕の定義 / 対照群の定義
3. **限界を明記する節を必ず置く**。「測れなかったもの」「条件に敏感なもの」
   「未実施の再測」を正直に書く。**これを省いた doc は後で覆る**
4. 自分の以前の数字を訂正するときは、**訂正であることを明示**して残す。消さない
