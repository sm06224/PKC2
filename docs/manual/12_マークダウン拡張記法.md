## 12.2 各 markup の詳細と例

### L-1 セクション区切り

```markdown
+++

+++ {role=section}
+++ {role=cover}
```

`+++` 単独行で改ページ / 区切り。`{role=...}` で意味付け:`section`(章) / `cover`(表紙) / `body`(通常) / `auto`(default)。Word / PPT export 時に role に応じてページ break や slide separator にマップされます(Phase 2 以降の export 機能で活きてきます)。

### L-2-a ハイライト

```markdown
本文中の ==重要== な事項。
```

`==` で囲んだ範囲が黄色マーカーになります。

### L-2-b 振り仮名(ルビ)

```markdown
[[ruby:漢字|かんじ]] を多用する文章で便利。
[[ruby:Tokyo|とうきょう]]
```

`[[ruby:本文|ふりがな]]` の形式。漢字以外でも英単語の発音表記などに。

### L-2-c 圏点(けんてん)

```markdown
[[em:重要]]事項
```

「圏点」は日本語特有の強調記号で、**各文字の上に「・」**を打って強調します。`<em>` の太字斜体とは別物の、文字単位の強調装飾。

### L-3 引用(CommonMark 標準)

```markdown
> 引用内容
> 複数行可
```

PKC2 独自挙動なし。CommonMark 標準のまま。

### L-4 コメント(render に出さないメモ)

```markdown
本文 %% この一文は再考、後で削除 %%

%%%
TODO: この section は仮置き。
最終版では削除する。
%%%
```

`%% ... %%` は同じ行内の inline コメント。`%%%` で囲んだ範囲は複数行のブロックコメント。**render すると完全に消えます**(CSS で hide ではなく出力自体に存在しません)。エクスポートしても残らないので、下書き段階のメモに最適。

### L-5 行頭アライン(段落寄せ)

```markdown
|| この段落はセンター寄せ。

|> この段落は右寄せ。

<| この段落は左寄せ(default なので明示は稀)。
```

行頭の `||` / `|>` / `<|` を置くと、その行から空行までの paragraph 全体が中央 / 右 / 左寄せになります。

**連続する別アライン行は別 paragraph として分離されます**(2026-05-07 確定挙動):

```markdown
|> 2026年5月8日

<| To: 関係者各位

|> From: 情報システム部
```

→ 3 個の独立 paragraph、それぞれ右 / 左 / 右寄せ。

### L-6 簡易インライン(色 / サイズ / 太字を組み合わせる)

```markdown
:重要:bold, red:
:大きく:lg, bg-yellow:
:120%サイズ:120%:
:総合:bold, italic, underline, red, bg-#fefce8:
```

`:文字:attrs:` の 3 区画で inline 装飾。attrs は半角カンマ区切り、複数併用可、順不同。

**vocabulary 一覧:**

| カテゴリ | 値 |
|--------|----|
| 強調 | `bold` / `italic` / `underline` / `strikethrough` / `code` |
| サイズ(段階式) | `xs` / `sm` / `md` / `lg` / `xl` / `2xl` / `3xl` |
| サイズ(自由値) | `120%` / `1.5em` / `0.75rem` / `12px` |
| 文字色 | CSS 色名 / `#hex` / `rgb(...)`(例 `red`、`#ff8800`)|
| 背景色 | `bg-<color>` / `bg-#hex`(例 `bg-yellow`、`bg-#000`) |
| font-family | `serif` / `sans` / `mono` |

**衝突回避**:`12:30:45` のような時刻表記は誤認識されません(`30` が attrs 語彙に当たらないため)。

### L-7 図 / 表 / 式 + 自動採番

```markdown
:::figure{#fig-architecture}
![](attachment:abc-image.png)
^^^ 全体構成
:::

本文 → 図 [@fig-architecture] を参照。
```

`:::figure{#id}` で開始、`:::` で閉じ、間の `^^^ caption` 行は省略可。`kind` を `figure` / `table` / `equation` のいずれかに切替可:`:::table{#tbl-1}` / `:::equation{#eq-1}`。

自動採番:同 entry 内の出現順で番号付与、caption に「図 1: ...」「表 1: ...」「式 1: ...」の prefix が自動付加されます。本文中で `[@fig-architecture]` と書くと「図 1」とリンク化されてクリックで対象に飛べます。

### L-8 空行マーカー(縦余白の明示)

```markdown
本文 1

_

本文 2(1 空行ぶん下)
```

```markdown
本文 1

_3

本文 2(3 空行ぶん下に大きく余白を取る)
```

`_` 単独行で 1 行ぶん、`_<N>`(N=1〜20)で N 行ぶんの余白。21 以上は 20 にクランプ。`_0` / `_3a` / `_word` 等は通常テキストとして残ります。CommonMark の連続空行 collapse 仕様で本文中に余白を制御できない問題を、明示マーカーで解決します。

### L-9 段落先頭 1 字下げ

```markdown
__段落本文。先頭の文字が 1 字下がります(日本語の段落字下げ慣習)。
__ 半角空白を挟んでも OK。
＿全角アンダースコアでも等価(U+FF3F)。
```

行頭 `__`(半角 `_` × 2)または `＿`(全角)で paragraph に 1 字下げ(`text-indent: 1em`)。

衝突回避:

- `___text___`(`_` 3 連続以上)は markdown horizontal rule なので字下げになりません
- `__bold__`(行末が `__` で閉じる)は markdown bold として処理、字下げになりません

**L-5 align prefix と併用可**:

```markdown
|| __センター + 字下げ
```

→ 中央寄せ + 字下げの両方適用。

## 12.3 行頭の空白系文字は無視されます

すべての行頭マーカー(L-1 / L-5 / L-8 / L-9)は、行頭の以下を **strip して** マーカー判定します:

- 半角スペース(任意の数)
- TAB(`\t`)
- 全角スペース(U+3000)

これにより、コピペでインデントが付いた状態でもマーカーが効きます。

## 12.4 Rich コピーで Word / ONLYOFFICE に貼る

PKC2 の **Rich コピー**(More メニュー → 🎨 Rich)を使うと、本文を inline `style="..."` 付きの HTML として clipboard に乗せます。Word / ONLYOFFICE / Gmail / Slack 等の rich-paste 先で:

- 中央寄せ / 字下げ段落 → そのまま中央 / 字下げ
- 黄色マーカー / 色付き太字 → そのまま色付きで貼り付き
- 圏点(text-emphasis)→ 対応 app では点が出る、未対応では plain `<em>` に graceful fallback
- 空行マーカー → Word の空段落として再現
- セクション区切り → 横線(`<hr>`)として再現

`docs/spec/markdown-dialect-for-ai-authors-v1.md` § 5(出力前 checklist)も併用すると、AI が生成した文書をそのまま Rich コピー → 業務 app に貼って体裁を整えるワークフローが実用的に回せます。

## 12.5 AI に PKC2 文書を書かせる(AI 規約書 v1 の活用)

AI(ChatGPT / Claude 等)に PKC2 の entry 本文を書かせるとき、**`docs/spec/markdown-dialect-for-ai-authors-v1.md`** を AI に prompt として渡すと、本章の markup を正しく使った文書を生成できます。

**典型ワークフロー:**

1. AI に `markdown-dialect-for-ai-authors-v1.md` の内容を貼り付け / 添付
2. 「以下の規約に従って PKC2 の markdown で〇〇を書いて」とお願い
3. 出力された markdown を PKC2 の text entry にペースト
4. 必要に応じて Rich コピーで Word / ONLYOFFICE に貼り付け
5. 体裁微調整のみで業務文書 / 通知文 / 報告書として使える状態になる

**AI 規約書 v1 の特徴:**

- self-contained(他 doc を参照しなくても規約だけで完結)
- 構文 / 衝突回避 / NG 例 / 出力前チェックリスト / 複合 fixture 例を 1 ファイルに集約
- マイナー追補は backward compat 必須(既存 markup の意味を変えない)
- メジャー破壊的変更は v2 として別ファイルに

**設計議論 / 業界事例 / IR 連動が知りたい方**は、別書 `docs/development/markdown-dialect-extensions-spec-2026-05.md`(human-oriented spec、~800 行)を参照してください。

## 12.6 Variables(`{{vars.x}}`、Phase 2 着地済 2026-05-08)

文書内変数。**frontmatter で定義した値を本文中で展開**できます。同じ文書を複数の宛先 / 用途で再利用するときに便利。

### 書き方

```markdown
---
vars:
  project: ALPHA-7
  client: Acme Corp
  date: 2026-05-08
  signature: 田中
---

# 案件 {{vars.project}} 進捗

本通知は {{vars.client}} 様向け、提出予定 {{vars.date}}。

|> 担当: {{vars.signature}}
```

→ render すると:

```
# 案件 ALPHA-7 進捗

本通知は Acme Corp 様向け、提出予定 2026-05-08。

                                                   担当: 田中
```

### 仕様

- `{{vars.<key>}}` で参照、`<key>` は英字始まり(`[A-Za-z_][\w-]*`)
- 内側空白は許容(`{{ vars.x }}` も OK)
- 改行を跨ぐ参照は無効(literal で残る)
- fenced code block(``` / ~~~)の中では展開しない
- inline backtick code span(`` ` `` ... `` ` ``)の中も展開される(2026-05-08 hotfix、`==xxx==` や `[[em:xxx]]` の中で展開できるようにするため)。literal にしたい場合は `\{{vars.x}}` で escape
- L-2 highlight / em-dot / ruby、L-6 simple-inline などの中身でも展開される
- escape は `\{{vars.x}}`(literal `{{vars.x}}` を出力)
- 未定義変数は **赤点線下線の警告**(`{{vars.unknown}}`)で残る → 気付いて修正できる
- `{{macros.x}}` / `{{export.x}}` 等 vars 以外の名前空間は Phase 2 では未対応(literal)

### TEXTLOG での使い方

TEXTLOG の各 log でも `---` fenced frontmatter で vars を定義可能。**log 単位で独立した variants** が作れます。

```markdown
---
vars:
  audience: 経営層
  project: ALPHA-7
---

# {{vars.project}} 状況報告

{{vars.audience}} 向け報告です。
```

(frontmatter 自体は preview に出ません、render で strip)

### AI 連携(宛先別 variant 生成)

ChatGPT / Claude 等に AI 規約書 v1 + 本節を流して、

> 「以下の vars だけ書き換えて、同じ本文を `経営層 / formal` 用と `現場 / casual` 用の 2 variant に分岐させて」

と指示すると、frontmatter の `vars` だけ差し替えた 2 つの entry を出力させられます。本文 1 つから複数の variant を AI prompting だけで生成できる、これが M-7 の主目的です。

## 12.7 reform-2026-05 Phase 2 着地分(2026-05-10、formal 記法 + 寛容 parse + 段組組版)

Phase 1(L-1〜L-9 + reform-2026-05 Phase 1 = `:::quote{author}` / `:role:[content]{attrs}` / `:::if{format}` / 4 形 align typo 寛容化)着地後の継続 wave で、以下が **追加実装** されました。詳細は AI 向け規約書 v2(`docs/spec/markdown-dialect-for-ai-authors-v2.md`)が canonical:

### 12.7.1 frontmatter document globals

```yaml
---
title: 報告書
writing: horizontal       # or vertical(縦書き、CSS writing-mode: vertical-rl)
direction: ltr            # or rtl(Arabic / Hebrew、横書き時 default align shift)
align: left               # horizontal: left/right/center、vertical: top/bottom/center
layout: a4-2col           # NEW、用紙 × 段組:a4/b5/letter/legal × 1/2/3 col
---
```

`layout: a4-2col` の組合せ 9 種(a4-1col / a4-2col / a4-3col / b5-1col / b5-2col / letter-1col / letter-2col / legal-1col / legal-2col)で、用紙幅 + 段組(column-rule 付)を CSS で render。screen は card 風 box-shadow、`@media print` で chrome off。見出し(h1/h2)は段抜き、figure / table / pre は段内固定。

### 12.7.2 formal inline / block 完全網羅

| 形 | simple 等価 | 用途 |
|----|-----------|-----|
| `:strong:[text]` | `**text**` | AI / serializer の formal emit |
| `:emphasis:[text]` | `*text*` | 同上 |
| `:code:[text]` | `` `text` `` | 同上 |
| `:strike:[text]` | `~~text~~` | 同上 |
| `:caption:[text]` | `^^^ text` | `:::figure` / `:::table` 内 caption |
| `:autoref:{id="fig1"}` | `[@fig1]` | id reference |
| `:::section{role=…}` | (新)| 8 role callout(summary / info / note / tip / important / warning / caution / danger)+ 色分け |
| `:::comment{block=true}` | `%%% … %%%` | block comment(完全 strip)|
| `:::break{kind=page\|rule}` | `+++` / `---` | section / page break |
| `:::paragraph{align=physical}` | (formal-only) | physical align(left / right / top / bottom / center)|

multi-line `[content]` 受理:`:emphasis:[\n本文\n]` のように改行を含む content が受理されます(blank line `\n\n` で reject)。

### 12.7.3 寛容 parse + canonical hint log(AI hallucination 救済)

AI(ChatGPT / Claude / Gemini)が Bootstrap / Tailwind / JSX / MDX 知識から **PKC2 にない formal 構文** を hallucinate しても、render し、推奨形を console と DOM attr で hint します:

| AI が書く形 | 寛容 parse 後 | console.info code | 推奨形 |
|------------|--------------|-------------------|--------|
| `:lead:[本文]` | `<span class="pkc-lead">本文</span>` | `[PKC2005]` | 普通の段落 + `==hl==` で強調 |
| `:spacing:{size=N}` | N 行 spacer | `[PKC2006]` | `_N`(L-8)|
| `:align:{position=end}` | **次段落を実際に右寄せ** | `[PKC2007]` | 行頭 `\|>`(L-5)|
| `:quote:{attribution=…}` | `<small class="pkc-attribution">…</small>` | `[PKC2008]` | block `:::quote{author=…}` |
| `:::note` `:::warning` `:::tip` ほか 8 role | `:::section{role=…}` alias | `[PKC2009]` | 直接 `:::section{role=…}` |
| `:::callout{type=X}` | 同上 | `[PKC2010]` | 同上 |
| `:::admonition{type=X title=Y}` | `:::section{role=X}` + `## Y` | `[PKC2011]` | 同上 + 個別 heading |

`?pkc-debug=hallucination` URL flag を付けると hint marker(dotted underline 等)が visible になり、user が canonical 形へ修正する gain が見えます。

### 12.7.4 `` ```html-render `` fence(HTML 直接 render)

複雑 layout / SVG / interactive widget は HTML 生成のほうが優れたケースに対応:

````markdown
```html-render
<div style="display: grid; grid-template-columns: 1fr 1fr;">
  <article>左カラム</article>
  <article>右カラム</article>
</div>
```
````

→ `<iframe sandbox="allow-scripts">` で隔離 render。CSP meta auto-inject(外部 fetch / 再帰 iframe 拒否)、postMessage auto-resize(cap 5000px)、`referrerpolicy="no-referrer"`。

### 12.7.5 em-dot `^^X^^` 内 nested inline parse

`^^**本気**^^` のように em-dot 内に bold / emphasis / code / highlight を入れて render できます。**asymmetric `*X**` / `**X*`** は em-dot 内 scope 限定で `**X**` に tolerant 正規化(user typo 救済)。

## 12.9 PKC-Markdown ハンズオン徹底ガイド(v2.3.0 確定)

ここまでの §12.1〜§12.8 は早見表 + 各 markup の最小例として整っています。本節は **「自分で TEXT エントリを 1 つ作って、写経しながら読む」前提のハンズオン** です。一読目は「こういう機能があるのか」と眺める用、二読目から実際に手を動かして試す用にデザインしました。

新規 TEXT エントリを 1 つ開いて、本節のサンプルを **コピーして貼り付け → save** すると、右側のプレビューで本節と同じ見え方になります。マニュアル自身がショーケースとして PKC-Markdown を full に使って書かれているので、「ここで紹介された記法は、いまあなたが目にしているマニュアルそのものに使われている」と確認できます。

### 12.9.1 まず最小サンプルを動かしてみる

新規 TEXT を作って、次の 5 行を本文に貼り付けてください。

```markdown
__本日の決定:採用案 ==A== を採択しました。
__理由は ^^情報セキュリティ^^ の観点から最適だからです。

|> 担当:[[ruby:山田太郎|やまだたろう]]
|> 提出:2026-05-16
```

プレビュー側では、

- 各段落の先頭が 1 字下がる(行頭 `__`)
- 「A」だけが黄色マーカーで強調される(`==X==`)
- 「情報セキュリティ」の各文字の上に「・」点が並ぶ(`^^X^^` 圏点)
- 末尾 2 行が右寄せで、「山田太郎」の上に小さく「やまだたろう」が付く(`[[ruby:base|rt]]`)

…が確認できます。これらは Word / PowerPoint へのエクスポートでも、ふりがなや段落字下げを含めて再現されます。本節以降は、この 5 つの記法を一例として、PKC-Markdown 全部を順に手を動かして覚えていきます。

### 12.9.2 装飾(インライン)を使い分ける

文章の中で「ここに目を留めてほしい」と読者に伝える装飾を、PKC-Markdown は **目的別に 10 種類** 用意しています。漫然と太字を多用する代わりに、目的別に使い分けると読みやすくなります。

#### 太字 / 斜体 / 取消 / 等幅 ── 用途で使い分ける

CommonMark 標準どおりに、`**太字**` `*斜体*` `~~取消~~` `` `等幅` `` がそのまま使えます。GFM 互換なので Notion / Obsidian / GitHub にコピーしても崩れません。

```markdown
**重要キーワード** はここを読めば全体の趣旨が掴める単位で使う。
*補足説明* や引用元の表題は斜体で。
~~v2.2.0 では未対応~~ → v2.3.0 で対応済み、のような version 履歴は取消線で対比。
コマンド名は `npm run build` のように等幅で囲んで、本文と区別する。
```

実際に **重要キーワード** はここを読めば全体の趣旨が掴める単位で使う、*補足説明* や引用元の表題は斜体で、~~v2.2.0 では未対応~~ → v2.3.0 で対応済みのような version 履歴は取消線、コマンド名は `npm run build` のように等幅で囲んで本文と区別、と render されているはずです。

AI(LLM)に PKC2 文書を生成させる時は、Formal 形 `:strong:[X]` `:emphasis:[X]` `:strike:[X]` `:code:[X]` を使うほうが parse の曖昧性が少なく、round-trip 安定性が高まります。AI prompt に「PKC formal 形で生成して」と書くと、AI 側もこの形式を選びやすくなります。

#### ハイライト ── `<mark>` 風の黄色マーカー

「読者に振り返ってほしい行」「会議録で次回への action item」「教科書の重要文」のような、太字より重い、けれど見出しにするほどではない、という強調には `==X==` を使います。デフォルトは ==黄色マーカー== の地色になります(soft yellow `#FFF3A0`、印刷 / プレゼンで威圧的にならないトーン)。

色を変えたいときは `==[color]X==` の形で角括弧の中に色を書きます。

```markdown
==[red]要対応== な項目は最優先で。
==[#fde68a]温かみのある hex 指定== もできるし、
==[rgb(0,0,255)]rgb() 関数== も受け付ける。
```

レンダリングすると、==[red]要対応== な項目は最優先で、==[#fde68a]温かみのある hex 指定== もできるし、==[rgb(0,0,255)]rgb() 関数== も受け付ける、と 3 種類の色が確認できます。色名は CSS の named color、`#xxx` `#xxxxxx` の 3-6 桁 hex、`rgb(r,g,b)` 関数、いずれの形式でも OK です。

会議録の典型例:

```markdown
## 2026-05-16 開発定例

- ==[red]Action== 担当者を月末までに決定
- ==[#10b981]Done== W24 着地、CI green
- ==[#3b82f6]Info== 次 wave は dependency update
```

これだけで read-only でも目的別の色付き作業リストになります。

#### 圏点 ── 日本語の文字単位強調

「太字や斜体では弱い、けれど見出し化するほどではない、文中の文字単位で重要箇所を示したい」── 日本語の組版ではこういう時に「圏点(けんてん)」を使います。各文字の上に小さな点を打って強調する伝統的な装飾です。

```markdown
PKC2 が ^^最も大切にしている^^ のは可換性です。
あるいは ..これは PKC-Markdown の代替形.. も使えます。
```

実際に、PKC2 が ^^最も大切にしている^^ のは可換性です、あるいは ..これは PKC-Markdown の代替形.. も使えます、と render されているはず。`^^X^^` と `..X..` は完全に等価で、PKC MD canonical 形では `..X..` に統一されます(round-trip で `^^` 形は `..` 形に正規化されます)。

文芸 / 公文書 / 教科書で「ここを覚えてほしい」のニュアンスで使うと効果的です。`<em>` 太字斜体とは別物の、日本語特有の文字単位強調と覚えてください。

#### ルビ ── 漢字に振り仮名、英語にカタカナ発音

人名・地名・専門用語・外来語に読み仮名を付けたい時、`[[ruby:漢字|かんじ]]` の形を使います。`|` の左がベース、右がルビ(rt)です。

```markdown
著者は [[ruby:中原 中也|なかはら ちゅうや]] です。
[[ruby:Tokyo|とうきょう]] と [[ruby:Kyoto|きょうと]] の文化的差異について
[[ruby:UNESCO|ユネスコ]] による世界遺産登録の動向
```

render では、著者は [[ruby:中原 中也|なかはら ちゅうや]] です、[[ruby:Tokyo|とうきょう]] と [[ruby:Kyoto|きょうと]] の文化的差異について、[[ruby:UNESCO|ユネスコ]] による世界遺産登録の動向、のようにベース文字の上に小さく読み仮名が出ます。

Word / PowerPoint へのエクスポート時は、docx ライブラリが本物の `<w:ruby>` element に未対応のため、近似として「ベース + 上付き(superscript)の小さな rt」で render します。印刷時には furigana 効果になるので、読み仮名としての機能は十分です。

#### 上付き / 下付き ── 数式や化学式の伴侶

科学・工学系の文章で頻出する上下付きは `:sup:[X]` `:sub:[X]` で書きます。Simple 形(`^X^` `~X~` のような対称 marker)は intentional に用意していません。これは `^^X^^` 圏点や `~~X~~` 取消線と曖昧になるからです。

```markdown
質量とエネルギーの関係:E = mc:sup:[2]
水分子の組成:H:sub:[2]O
速度:平均 v̄ = (v:sub:[1] + v:sub:[2]) / 2
```

実際に、質量とエネルギーの関係:E = mc:sup:[2]、水分子の組成:H:sub:[2]O、速度:平均 v̄ = (v:sub:[1] + v:sub:[2]) / 2、と上下付きが交互に出ているのが確認できます。

#### 数式 ── LaTeX 互換の inline / block math

LaTeX 互換の数式記法を `$...$` で囲んで書きます。

```markdown
ピタゴラスの定理は $a^2 + b^2 = c^2$ で表される。

二次方程式の解の公式:

$$x = \frac{-b \pm \sqrt{b^2 - 4ac}}{2a}$$
```

inline 形 `$X$` は本文中に埋め込み、block 形 `$$X$$` は中央寄せ + 上下余白付きの displayed equation になります。Word 出力時は Cambria Math フォント + italic で「数式らしい見た目」になります。本格的な OMML(Office Math)native render は今後の wave で対応予定で、現時点では「source は完全保存 + ラウンドトリップ可能、見た目は近似」というステータスです。

文書中で同じ数式を何度も参照したい時は、`:::figure{#eq-mass-energy kind=equation}` ブロックで囲んで `[@eq-mass-energy]` で本文中から参照できます(後述の §12.9.3)。

#### 脚注 ── 学術・技術文書で頻出するアレ

「本文の流れを切らずに、注釈や引用元を末尾にまとめたい」というときに脚注を使います[^note-footnote]。本文中で `[^id]` の形で参照し、末尾(または source 上の任意の位置)に `[^id]: 注釈の本文` で定義します。

[^note-footnote]: これがその脚注定義の例です。マニュアルの末尾に「脚注領域」が自動的にできて、ここに本文が並びます。複数の脚注を持つ文書では、自動的に 1, 2, 3 と番号付けされます。

```markdown
PKC2 は AST commutative IR を採用しています[^ast-ir]。
これによって Word / PPT 出力でも同じ意味を保てます[^export]。

[^ast-ir]: AST commutative IR の詳細は `docs/spec/ast-commutative-ir.md` を参照。
[^export]: docx は `FootnoteReferenceRun`、HTML は `<sup class="footnote-ref">` を出力。
```

HTML 出力では `<sup class="footnote-ref">` で本文中に上付き番号、末尾に `<section class="footnotes">` で number list、という標準的な脚注表現になります。Word 出力では `Word の真の脚注機能` に変換され、ページ下部に番号付きで表示されるので、印刷物としても十分使えます。

#### 変数 ── 同じ語を 1 箇所書き換えで全部更新

「製品名」「バージョン番号」「日付」など、文書中で何度も繰り返す語は、frontmatter に変数として定義しておくと一括で書き換えできます。

```markdown
---
vars:
  product_name: "PKC2"
  version: "v2.3.0"
  release_date: "2026-05-16"
---

# {{vars.product_name}} {{vars.version}} リリースノート

{{vars.product_name}} は {{vars.release_date}} にリリースされました。
本書では {{vars.version}} の新機能を紹介します。

## 互換性

{{vars.version}} は v2.2.0 と完全互換です。
```

`{{vars.x}}` を本文中に書くと、frontmatter の `vars.x` 値で展開されます。未定義の `{{vars.unknown}}` を書いた場合、PKC2 は **`[未定義: vars.unknown]` を赤 italic で表示** して silent fail を避けます。これは [§15 PKC Hint 機構](./15_pkc_hint_機構.md) の実装済 hint の 1 つで、編集中に見落としを catch できます。

#### コメント ── 本文に出ない執筆中メモ

「執筆中の思考メモを source に残したいが、render 結果には出したくない」というときは `%% メモ %%` で行内コメント、`%%%` 〜 `%%%` で複数行コメントです。

```markdown
本日の議題:

%% TODO: 議題 3 の根拠データを後で追加 %%

%%%
ここは AI による下書きセクション
最終 review 後に削除 / 整形すること
%%%

議題 1:Wave Z 完了報告
```

両方のコメント記法は render から完全に消えるので、docx / pptx エクスポートにも影響しません。執筆中のメモ、TODO、AI prompt の hint、レビュー用のコメント、すべて source に残しつつ output には反映しない、という使い方ができます。

#### 任意 span ── CSS class 風指定で見た目を細かく

「ハイライトでも太字でもなく、もうちょっと細かく指定したい」というときは Simple inline `:本文:attr1,attr2:` 形が使えます。

```markdown
:この語を強調:bold,red:
:大きく:lg:
:背景黄色:bg-yellow,black:
:150% サイズ:150%:
```

attrs は `,` か space 区切りで、CSS class として組み合わせて使えます。`%` `#` `_` `,` `.` `-` を含む値も受け付けます。class は base.css 側で `.bold` `.red` `.lg` 等として定義されていれば見た目に反映され、定義されていない class は無視されます(壊れません)。

id や任意の key=value 属性を渡したいときは Formal 形:

```markdown
:span:[警告テキスト]{class=warn #err-01 data-type=critical}
```

R-E-3 の正式 syntax で、`#id` `key=value` を全部 attrs として保持できます。

### 12.9.3 構造(ブロック)を使い分ける

文書の構造を表現する、より大きな単位の記法です。「行頭 marker」と「`:::role{attrs}` 〜 `:::` ブロック」の 2 系統あります。

#### 行頭 marker ── 1 行で段落のレイアウトが決まる

行の先頭に置くだけで段落のレイアウトを変える marker が 5 種類あります。

**`+++` セクション区切り**:章の終わり、強い区切り、改ページ。

```markdown
ここまでが第 1 章。

+++

第 2 章のはじめ。
+++ {role=section}
別の区切り role 指定も可。
```

Word 出力では `+++` のところで実際に改ページが入ります。`+++ {role=section}` のように role attrs を付けると、PowerPoint 出力ではセクション扉スライドの開始 marker として解釈されます。

**`_` または `_N` で空行**:N 行ぶんの縦余白(N は 1〜50)。

```markdown
ここで一旦区切る。

_3

3 行分の縦余白を空けてから次の話題へ。
```

普通の Markdown は空行を何個書いても 1 つの blank として処理しますが、`_3` のように明示すると 3 行分の縦余白が確保されます。発表資料のスライド組み立てや、紙面の余白制御で使います。N>50 は cap されて警告 hint が出ます(§15)。

**`__段落本文`(半角 2)または `＿段落本文`(全角 1 字)で 1 字下げ**:日本語慣習の段落字下げ。

```markdown
__この段落の頭が 1 字下がります。日本語の縦書き文書では基本ですが、Web では珍しい。Word / 印刷出力では正しく字下げされます。
__次の段落も同じく字下げ。
```

半角 `__` と全角 `＿` は完全に等価で、AI / user の typing 習慣に合わせて好きに使えます。

**`||X` 中央寄せ / `|>X` `<|X` `|<X` `>|X` 右寄せ**:段落の物理 align を行頭 marker で。

```markdown
|| この段落は中央寄せ
|> この段落は右寄せ(end)
<| この形も end に正規化される
|< これも end
>| これも end
```

右寄せ 4 形(`|>` `<|` `|<` `>|`)は意図的に用意していて、AI が `|>` を `<|` に typo しがちな問題を吸収します。すべて right align(end 寄せ)として処理されます。

:::section{role=tip}
**全 marker は行頭の空白に寛容です**。半角スペース・タブ・全角スペース(U+3000)が何個続いていても、PKC2 が吸収して marker として認識します。`   __段落` も `	|>右寄せ` も `　_3` も期待通り動きます。Web エディタ間でコピー&ペーストするときに、見えない空白が挟まっても壊れないように設計されています。
:::

#### `:::section{role=ROLE}` ── 8 色の callout box

「ここから注意事項です」「これは Tip です」「警告」のような、本文から区切られた情報ブロックには `:::section{role=ROLE}` を使います。8 つの role があります。

```markdown
:::section{role=note}
**Note** 補足説明、参考情報。青系の icon と色。
:::

:::section{role=tip}
**Tip** 上手な使い方、コツ。緑系の icon と色。
:::

:::section{role=info}
**Info** 情報提供、追加コンテキスト。青系の icon と色。
:::

:::section{role=warning}
**Warning** 注意事項、起こりうる問題。オレンジ系の icon と色。
:::

:::section{role=caution}
**Caution** より強い注意、ミスしやすい箇所。オレンジ系。
:::

:::section{role=important}
**Important** 重要事項、見逃すと損失が出る情報。赤系。
:::

:::section{role=danger}
**Danger** 危険、データ消失リスク等。赤系。
:::

:::section{role=summary}
**Summary** 要点まとめ、章末の振り返り。紫系。
:::
```

それぞれ icon + 色 + 罫線のセットで本文から視覚的に区切られた callout box になります。HTML / Word / PowerPoint 全てで同じ意味で render されます。本マニュアル内でも、tip / warning / important / note を随所で使っています。

#### `:::quote{author="..." year=... source="..."}` ── 著者付き引用

引用文に著者情報を構造的に持たせたい時は、`:::quote` ブロックを使います。

```markdown
:::quote{author="Donald Knuth" year=1974 source="Computing Surveys"}
Premature optimization is the root of all evil.
:::
```

引用本文の後に italic + 右寄せで「— Donald Knuth, 1974, Computing Surveys」のような attribution が自動で付きます。著者・年・出典が source markdown に構造として残るので、Pandoc 経由で BibTeX / 学術引用形式に変換しやすくなります。

#### `:::figure{#id}` ── 図 / 表 / 式の自動採番 + 本文参照

```markdown
:::figure{#fig-architecture}
![PKC2 構成図](asset:diagram-arch.png)
^^^ PKC2 v2.3.0 のアーキテクチャ全体
:::

本文中で [@fig-architecture] を参照してください。
```

`^^^` の行が figure の caption(キャプション)になり、自動で「図 1: PKC2 v2.3.0 のアーキテクチャ全体」のような番号付きの caption に展開されます。`[@fig-architecture]` は本文中で「図 1」と展開されます。

表や式にしたい場合は `kind` を指定します:

```markdown
:::figure{#tbl-results kind=table}
| 指標 | v2.2.0 | v2.3.0 |
|------|--------|--------|
| Test | 7100   | 8067   |
:::

:::figure{#eq-energy kind=equation}
$$E = mc^2$$
:::
```

`kind=table` で「表 1」「表 2」、`kind=equation` で「式 1」「式 2」と auto-numbering 名が変わります。文書全体で番号が連続するので、後から図を追加・削除しても番号がずれません。

#### `:::if{format=...}` ── 出力形式ごとに内容を切替

「HTML で表示する時はリッチに、Word に書き出す時はテキストのみ」のように、出力形式ごとに内容を切り替えたい場合に使います。

```markdown
:::if{format=html}
このセクションは HTML 表示時のみ表示されます。インタラクティブな図など。
:::

:::if{format=docx}
このセクションは Word エクスポート時のみ表示。印刷向けの追加説明など。
:::

:::if{format=pptx}
このセクションは PowerPoint エクスポート時のみ表示。発表者ノートなど。
:::

:::if
format 指定なしの if ブロック。常に表示されます。
:::
```

format に指定がない、または `format=any` の場合は、すべての surface で表示されます。同じ document を HTML / Word / PowerPoint で別の体裁にしたい時に活躍します。

#### `:::break{kind=...}` ── 改ページ / 罫線の formal 形

`+++` の Formal 形です。`kind=page` で改ページ、`kind=rule` で水平線。

```markdown
:::break{kind=page}
:::break{kind=rule role=appendix}
```

`+++` と等価ですが、`role` を含む明示的な attrs を持たせたい時、AI が生成する厳密形として使うのに向いています。PKC MD canonical 形では `+++` を採用しているので、PKC MD copy → paste の round-trip で `:::break{kind=page}` は `+++` に正規化されます。

#### `:::paragraph{align=...}` ── 段落 align の Formal 形

行頭 `||` `|>` の Formal 形です。

```markdown
:::paragraph{align=center}
このブロック全体が中央寄せされます。
複数行の段落でも有効。
:::
```

PKC MD canonical 形では行頭 marker(`||`、`|>`)を採用するので、PKC MD round-trip 後はこちらの形に正規化されます。AI が `:::paragraph{align=center}` を Formal で生成しても、内部 AST 上は同じ `AstParagraph.align='center'` になります。

#### `:::comment` ── Formal 形の複数行コメント

`%%%` 〜 `%%%` の Formal 形。

```markdown
:::comment
本セクションは執筆途中。
2026-06 までに完成予定。
:::
```

render から完全に消えるのは `%%%` と同じ。AI が hallucinate で `<!-- HTML comment -->` を書いた場合の代替形、または attrs(`visibility=hidden` 等)を将来追加したい時の伸びしろとして用意されています。

:::section{role=tip}
**`:::` ブロックは任意深度でネスト可能** です。`:::if{format=html}` の中に `:::section{role=note}`、その中に `:::figure{#diag1}` を入れる、というネストが普通に動きます。PKC2 は parse 時に `:::` 各行を独立段落に正規化して closer ペアを正しく検出するので、深くネストしても壊れません。
:::

:::section{role=warning}
**閉じ忘れにも寛容**:`:::quote{author="No Close"`(`}` 閉じ忘れ)や `:::` closer を書き忘れたままでも、PKC2 は壊れません。`}` 忘れの場合は role 部分(`:::quote`)のみ採用して attrs は drop、closer 忘れの場合は EOF まで(または次の `:::role` opener が現れるまで)の content を取り込みます。AI が雑に書いた markdown でも、可能な限り意図を汲んで render する「寛容 parse doctrine」の現れです。
:::

### 12.9.4 frontmatter ── 文書ヘッダーで全体設定

文書の先頭に `---` 〜 `---` で囲んだ YAML ブロックを置くと、文書全体の global 設定ができます。

```yaml
---
notation: pkc-markdown-1.0    # 方言 ID(明示的に書かなくても OK)
title: ドキュメント表題
author: 著者名
vars:                          # 変数定義(本文で {{vars.x}} 展開)
  project_name: "PKC2"
  milestone: "2026-05"
writing: horizontal            # horizontal / vertical(縦書き)
direction: ltr                 # ltr / rtl(右から左)
align: left                    # 全体のデフォルト align
layout: a4-2col                # 出力 layout
---
```

`layout` が Word / PowerPoint 出力で **段組 + 用紙サイズ** に反映されます。利用可能な 9 種類:

- `a4-1col` / `a4-2col` / `a4-3col` ── A4 縦、1〜3 段組
- `b5-1col` / `b5-2col` ── B5 縦、1〜2 段組
- `letter-1col` / `letter-2col` ── US Letter、1〜2 段組
- `legal-1col` / `legal-2col` ── US Legal、1〜2 段組

例:`layout: a4-2col` を frontmatter に書いた文書を Word エクスポートすると、A4 縦の 2 段組レポート体裁になります。PowerPoint エクスポートでは、対応する 2 列割付スライドになります。学術論文や業務レポートで「2 段組で書きたい」と決まっている時に、本文を一切変更せず frontmatter 1 行で対応できます。

frontmatter は省略してまったく問題ありません。普通の user は触らず、AI に「2 段組レポートとして生成して」のような形式指定を伝えたい時、または変数を使い回したい時にだけ書きます。

### 12.9.5 寛容 parse ── AI hallucination を救う設計

PKC2 は AI(LLM)が PKC-Markdown を生成する未来を見据えて設計されています。しかし AI は時として、Web で広く使われている別の Markdown 方言(MkDocs、Material for MkDocs、Quarto、Docusaurus 等)の記法を mix-up して出力することがあります(これを「hallucination」と呼びます)。

PKC2 はそのような hallucinated input を **silent fail させずに、canonical 形と等価に処理する** ように作られています。代表的な寛容パターンを以下に挙げます。

#### `:::note` / `:::warning` / `:::tip` 単独形

AI が MkDocs 風に `:::note` `:::warning` `:::tip` のような単独 role 名でブロックを書いた場合、PKC2 は `:::section{role=note}` 等価として処理します。同時に `console.info` で「canonical 形は `:::section{role=note}` です」とログを出します(将来の AI repair tool が学習に使えるように)。

```markdown
:::note
これは MkDocs 慣習で AI が書きがちな形。
PKC2 はこれを :::section{role=note} 等価として render。
:::
```

#### `:::callout{type=warning}` や `:::admonition{type=warning title=Title}`

Material for MkDocs / Docusaurus 由来の形も同じく `:::section{role=warning}` に正規化されます。`title` 属性は `## Title` 見出しに格上げします。

#### `:lead:[X]` / `:quote:{attribution=X}` inline alias

`:lead:[content]` のような lead-paragraph 風の inline は `<span class="pkc-lead">` で wrap して見た目を出します(canonical は通常段落で **強調を意図しない**)。`:quote:{attribution=X}` のような inline attribution は `<small class="pkc-attribution">— X</small>` で render します(canonical は block 形 `:::quote{author="X"}`)。

#### 閉じ忘れ寛容

`:::quote{author="No Close"`(`}` 忘れ)も寛容に受けます。role 部分(`:::quote`)を opener として認識し、attrs は drop、content は EOF まで(または次の opener まで)取り込みます。連続 `:::\n:::` も正しく独立 closer として認識します。行頭の tab や全角スペースも leading whitespace strip して認識します。

このような寛容 parse の挙動を **意図的に活用する** ことは推奨しません。AI が偶発的に hallucinate した時のセーフティネットであり、自分で書く時は canonical 形(`:::section{role=note}` / `:::quote{author=X}` 等)で書いたほうが意図が明確で round-trip も安定します。

### 12.9.6 PKC MD ↔ HTML 不変式 ── 別 entry に貼っても render が変わらない

:::section{role=important}
PKC2 の最重要 invariant は **「PKC MD = Rendered HTML」**。📋 PKC MD ボタンでコピーしたテキストを別の entry に貼り付けて再 render した結果が、元の entry の HTML と完全同一になります。
:::

これがなぜ大事なのか、典型シナリオで確認できます。

**シナリオ:複雑な markup を含む文書を別の entry に複製する**

1. 元の entry を開く。本文には `:::section{role=note}` のブロックや `^^圏点^^`、`==[red]X==`、`[[ruby:漢字|かんじ]]` 等が混在している
2. More… メニュー → 📋 PKC MD をクリック。クリップボードに canonical 形の PKC-Markdown が入る
3. 新規 TEXT エントリを作って本文に貼り付け、save
4. プレビューを開く

すると、新しい entry のプレビューが元の entry とまったく同じ見た目になります。`^^X^^` が `..X..` に正規化されていても、`{base|rt}` が `[[ruby:base|rt]]` になっていても、`{align=center}` が行頭 `||` marker に変換されていても、表示は同一です。

これは「source markdown ≡ AST ≡ Rendered HTML の 3 表現が完全に可換」という設計の現れで、ファイル形式間の壁を最小化するための PKC2 の基本姿勢を支えています。Word / PowerPoint への変換、AI への AST 渡し、外部エディタとの相互運用、すべての downstream 処理がこの invariant を起点に組み立てられています。

### 12.9.1 設計思想 ── 3 階層の文法

PKC-Markdown は **3 階層の文法** を同時に satisfy する設計になっています。これは「人間が日常 typing で書きやすい形」「AI が機械的に生成しても安全な厳密形」「typo や hallucination(LLM の幻覚)を寛容に受け止める alias 形」の三つを、1 つの parser で一貫して扱う ── という戦略です。

**1 階層目:Simple 形(人間が typing する短い形)**

`**太字**` `==ハイライト==` `^^圏点^^` のような、Markdown の慣習に近い 2-3 文字の対称 marker。日常文書を書く user(あなた)はこれだけ覚えれば 90% の文章は書けます。読みやすさを優先しているので、source markdown だけを見ても何が起きるか直感的に分かります。

**2 階層目:Formal 形(機械が生成する厳密形)**

`:strong:[太字]` `:::section{role=note}` のような Pandoc 風の attrs syntax を持つ形。**AI(LLM)に「PKC2 文書を生成してほしい」と頼むときの推奨形** です。属性が明示的なので、parse の ambiguity がなく、AST IR への変換が安定し、PKC MD → 別 entry に貼り付け → 再 render で完全同一になります(後述する supreme invariant)。

**3 階層目:寛容 alias 形(typo / hallucination の救済)**

AI が `:::note` `:::callout{type=warning}` のような MkDocs / Material 由来の形で書いてしまったり、`}` を閉じ忘れたり、行頭に tab を入れてしまったりしても、PKC2 は **canonical 形に勝手に整流して動かす** ように作られています。これは Postel's Law(寛容に受け、厳密に送る)を実装したもので、AI hallucination tolerance とも呼びます。Web に流通する markdown 方言は乱立しているので、その bleed-through を受け止める安全網として機能します。

### 12.9.2 装飾(inline)記法を順番に

#### 太字 / 斜体 / 取消 / コード

CommonMark 標準の `**太字**` `*斜体*` `~~取消~~` `` `コード` `` は全てそのまま使えます。GFM 互換なので Notion / Obsidian / GitHub と相互運用できます。これら 4 つには Formal 形もあり、`:strong:[太字]` `:emphasis:[斜体]` `:strike:[取消]` `:code:[コード]` と書けます。AI に文書を生成させる時は Formal 形のほうが parse 安定性が高いので、prompt に「PKC formal 形で出力して」と指示すると round-trip 安定性が上がります。

#### ハイライト(`==X==`)と色ハイライト(`==[color]X==`)

`==重要な箇所==` で `<mark>` 風の黄色マーカー(`#FFF3A0` の soft yellow、印刷 / プレゼンで威圧的にならないトーン)になります。これは GFM の `<mark>` HTML 直書きと等価で、Word / Notion などへの rich コピー時にもネイティブ `<mark>` として運ばれます。

色を指定したい時は `==[red]赤い文字==` のように `[]` の中に色名 / hex / rgb() を入れます。具体例:

```markdown
==[red]赤名指定==、==[#fde68a]hex 6 桁==、==[rgb(0,0,255)]rgb() 関数==
```

render すると ==[red]赤名指定==、==[#fde68a]hex 6 桁==、==[rgb(0,0,255)]rgb() 関数== のようになります。色名は CSS named color の任意のもの、`#xxx` `#xxxxxx` の 3-6 桁 hex、`rgb(r,g,b)` の関数表記、すべて受け付けます。

#### 圏点(`^^X^^` または `..X..`)

日本語特有の文字単位強調装飾「圏点(けんてん)」を `^^重要^^` または `..重要..` で書けます。「各文字の上に小さな点を打って強調する」装飾で、`<em>` の太字斜体とは別物です。^^本当に重要なところ^^ のように、文芸 / 公文書 / 教科書で使われる強調表現を Web / Word でも維持できます。`^^` と `..` は完全に等価ですが、PKC MD canonical 形では `..X..` を採用しています(round-trip 後はこちらに正規化されます)。

#### ルビ(振り仮名)

漢字や英単語に振り仮名 / 読み仮名を付けたい場合、`[[ruby:漢字|かんじ]]` の形を使います。`|` の左がベース、右がルビ(rt)です。

```markdown
[[ruby:漢字|かんじ]] や [[ruby:Tokyo|とうきょう]] のように
```

render すると [[ruby:漢字|かんじ]] や [[ruby:Tokyo|とうきょう]] のように、ベース文字の上に小さく読み仮名が出ます。Word / PPT 出力でも、docx ライブラリが本当の `<w:ruby>` element を未サポートのため、近似として「ベース + 上付き(superscript)の小さな rt」で render します(印刷時 furigana 効果)。

#### 上付き(`:sup:[X]`)と下付き(`:sub:[X]`)

数式や化学式の上下付き文字。`E = mc:sup:[2]` で E = mc² 風に、`H:sub:[2]O` で H₂O 風に出ます。Formal 形のみ用意しています(`^X^` `~X~` 等の Simple 形を Markdown に追加すると `*斜体*` 等と曖昧になるためです)。

#### 数式(`$X$` / `$$X$$`)

LaTeX 互換の数式記法を `$x^2 + y^2 = z^2$` のように `$` で囲んで書きます。$$x^2 + y^2 = z^2$$ のように `$$ ... $$` で囲むと display block(中央寄せ・上下余白あり)になります。

PKC2 内部では math 記法を AST node に保持し、Word 出力時には Cambria Math フォント + italic で「数式らしい見た目」に整えます。本格的な OMML(Office Math)native や、画面上での KaTeX レンダリングは今後の wave で対応予定ですが、現状でも source markdown は完全保存 + ラウンドトリップ可能です。

#### 脚注(`[^id]` + `[^id]: 本文`)

学術 / 技術文書で頻出する脚注を `参照する本文 [^note1]` のように本文中で `[^id]` で参照し、末尾に `[^id]: 脚注本文` で定義します[^note1]。

[^note1]: これがその脚注定義の例です。本マニュアルの末尾(章末ではなく document 末)に「脚注領域」が自動的にできて、ここに本文が並びます。

HTML 出力時は `<sup class="footnote-ref">` + 末尾 `<section class="footnotes">` の標準的な脚注表現になります。Word 出力時は **`FootnoteReferenceRun` + `Document.footnotes` API** で **Word の真の脚注機能** に変換され、page 下部に numbered list で表示 + Outline View / 印刷でも参照リンクが機能します(2026-05-16 の PR-W18 で確定)。

#### 変数(`{{vars.x}}`)

frontmatter で定義した `vars` を本文中で `{{vars.project_name}}` のように展開します。同じ語(製品名、版数、日付など)を文書中で何度も使う時、1 箇所書き換えれば全部更新できます。未定義の `{{vars.unknown}}` を書いた場合、PKC2 は **`[未定義: vars.unknown]` を赤 italic で表示** して警告します(silent fail はしません)。これは [15 章 PKC Hint 機構](./15_pkc_hint_機構.md) の実装済 hint の 1 つです。

#### コメント(`%% X %%` と `%%% ... %%%`)

`%% この文字列は本文に出ない %%` で行内コメント、`%%%` 〜 `%%%` で複数行コメント。両方とも render 結果には一切残らない(完全に消える)ので、執筆中のメモ書きや、AI prompt の hint として使えます。完全削除なので docx / pptx 出力にも影響しません。

#### Simple inline `:text:attrs:`(L-6)

任意の CSS class 風指定で span を作りたい時、`:本文:attr1,attr2,attr3:` のように **3 つのコロンに挟まれた形** で書きます。例:

```markdown
:太字赤大:bold,red,lg:
:背景黄色:bg-yellow,black:
:150% サイズ:150%:
```

attrs は `,` か space 区切りで、CSS class 風に組み合わせて使えます。`%` `#` `_` `,` `.` `-` を含む値も accept します(寛容 char class)。CSS class は base.css 側で `.bold` `.red` `.lg` 等として定義されていれば見た目に反映されます。AST 上は `AstSpan` の `attrs.classes` に格納されるので、PKC MD round-trip で形は完全保存されます。

属性に id や key=value を渡したい時は Formal 形 `:span:[本文]{#id key=value class=foo}` を使います。R-E-3 の正式 syntax です。

### 12.9.3 構造(block)記法を順番に

#### 行頭 marker(L-1 / L-8 / L-9 / R-C)

行の先頭に置くだけで段落のレイアウトを変える marker が 5 種類あります。

`+++` で **セクション区切り**(改ページ / 強い区切り)。`+++ {role=section}` のように role を付けると Word 出力で章の終わりや扉ページ前の区切りに mapping されます。

`_` または `_3` のように _ の後に数字を続けると **N 行ぶんの空行**(blank-line marker)になります。N は 1〜50 の範囲で、超えた場合は cap されて警告 hint が出ます。例えば `_3` を書くと、render 結果で 3 行ぶんの縦余白が空きます。

`__段落本文` または `＿段落本文`(全角)で **段落の先頭 1 字下げ**(日本語慣習)。__この段落のように、行頭に `__` を置くだけで字下げします。Word / Word 互換 EAW 句読点で正しく表示されます。

`||中央寄せ` で **段落の中央寄せ**。`|>右寄せ` `<|右寄せ` `|<右寄せ` `>|右寄せ` のいずれでも **右寄せ(end 寄せ)** になります。R-C は「`||` center + end 4 形」の 5 形を用意していて、これは AI が `|>` を `<|` に typo しがちな問題への対策です(4 形すべてを end として扱う寛容 parse)。

**全ての行頭 marker は行頭の空白に寛容です**。半角スペース・タブ・全角スペース(U+3000)が何個続いていても、PKC2 が吸収して marker として認識します。`   __段落` も `\t\|>右寄せ` も `　_3` も、すべて期待通りに動きます(2026-05-16 の PR-W24 で確定)。

#### Formal block(`:::role{attrs}` 〜 `:::`)

PKC-Markdown の大きな特徴の 1 つが、`:::role{attrs}` 〜 `:::` という対で囲む block 構造です。MkDocs / Material / Quarto などで広く使われている形を採用しています。

:::section{role=note}
**:::section{role=ROLE}** が用意するのは「callout box」と呼ばれる、本文と視覚的に区別された情報ブロックです。8 つの role があり、`warning` `note` `info` `tip` `caution` `important` `danger` `summary` のいずれかを指定すると、それに応じた icon と色のセットで囲み box になります。本マニュアル内でもこのように tip / warning / important を使っています。
:::

**`:::quote{author="X" year=Y source="Z"}` 〜 `:::`** は著者付き引用です。本文の引用が終わった後、末尾に italic + 右寄せの「— Author, Year, Source」形式で attribution が自動で付きます。著者情報を構造的に保持できるので、Pandoc 経由で BibTeX / 学術形式に変換しやすくなります。

**`:::figure{#id} 〜 ^^^ caption 〜 :::`** は図 / 表 / 式のブロックで、自動採番つきです。デフォルトは「図 1」「図 2」と進み、`:::figure{#fig-x kind=table}` のように `kind=table` を指定すると「表 N」、`kind=equation` で「式 N」になります。本文中で `[@fig-x]` と書けば「図 1」と展開される auto-reference になります。

**`:::if{format=html|docx|pptx|any}` 〜 `:::`** は条件付きレンダリングです。指定した format に出力する時だけ block の中身が出る、それ以外では完全に消える、という挙動。HTML 表示用と Word 出力用で内容を切り替えたい時に使います。format='any' または format='' 指定なしの場合は常に表示します。

**`:::break{kind=page|rule role=R}`** は self-closing(中身なし)の改ページ / 罫線です。`+++` の Formal 形と等価です。kind=page で改ページ、kind=rule で水平線。AST 上は同じ AstBreak ノードとして扱われます。

**`:::paragraph{align=center|end|start|left|right}`** は段落の物理 align を attrs で指定する block。行頭 marker `||` `|>` の Formal 形に相当します。

**`:::comment` 〜 `:::`** は複数行ブロックコメントの Formal 形(`%%%` 〜 `%%%` と等価)で、render から完全に消えます。

:::section{role=tip}
**ネストは任意深度可能** です。`:::if{format=html}` の中に `:::quote{author="X"}` を入れ、さらにその中に `:::figure{#f}` を入れる、というネストが普通に動きます。PKC2 は parse 時に `:::` 各行を独立 paragraph に正規化して closer ペアを正しく検出するので、深くネストしても壊れません。
:::

:::section{role=warning}
**閉じ忘れ寛容**:`:::quote{author="No Close"` のように attrs の `}` を閉じ忘れたり、`:::` closer を書き忘れたりしても、PKC2 は壊れません。`}` 忘れの場合は role 部分(`:::quote`)のみ採用して attrs は drop、closer 忘れの場合は EOF まで(または次の `:::role{` opener が現れるまで)の content を取り込みます。AI が雑に書いた markdown でも、可能な限り意図を汲んで render するという「寛容 parse doctrine」の現れです。
:::

### 12.9.4 frontmatter(文書ヘッダー)

文書の先頭に `---` 〜 `---` で囲んだ YAML ブロックを置くと、文書全体のグローバル設定ができます。

```yaml
---
notation: pkc-markdown-1.0    # 方言 ID(明示的に書かなくても OK)
title: ドキュメント表題
author: 著者名
vars:                          # 変数定義(本文で {{vars.x}} 展開)
  project_name: "PKC2"
  milestone: "2026-05"
writing: horizontal            # horizontal / vertical(縦書き)
direction: ltr                 # ltr / rtl(右から左)
align: left                    # 全体のデフォルト align
layout: a4-2col                # 出力 layout
---
```

`layout` 指定は Word / PowerPoint 出力で段組 + 用紙サイズに反映されます。利用可能な 9 種:`a4-1col` / `a4-2col` / `a4-3col` / `b5-1col` / `b5-2col` / `letter-1col` / `letter-2col` / `legal-1col` / `legal-2col`。例えば `layout: a4-2col` を frontmatter に書くと、Word 出力は A4 縦の 2 段組レポート体裁になります。PowerPoint 出力は対応する 2 列割付スライドになります。

frontmatter は省略してもまったく問題ありません。普通の user は触らず、AI に「2 段組レポートとして生成して」のような形式指定を伝えたい時、または変数を使い回したい時にだけ書きます。

### 12.9.5 寛容 parse(Postel's Law、AI hallucination 対策)

PKC2 は AI(LLM)が PKC-Markdown を生成する未来を見据えて設計されています。しかし AI は時として、Web で広く使われている別の markdown 方言(MkDocs、Material for MkDocs、Quarto、Docusaurus 等)の記法を mix-up して出力することがあります(これを「hallucination」と呼びます)。

PKC2 はそのような hallucinated input を **silent fail させずに、canonical 形と等価に処理する** ように作られています。代表的な寛容パターンを以下に挙げます:

`:::note` `:::warning` `:::tip` 等(role を block 名にした形)を AI が書いた場合、PKC2 は `:::section{role=note}` 等価として処理します。同時に `console.info` で「canonical 形は `:::section{role=note}` です」とログ出力(将来の AI repair tool が学習できるようにするため)。

`:::callout{type=warning}` や `:::admonition{type=warning title=Y}` といった MkDocs / Material 由来の形も、同じく `:::section{role=warning}` に正規化されます。`title` を `## Y` 見出しに格上げするなど、source の意味を最大限保ちます。

`:lead:[content]` のような lead-paragraph 風の inline を AI が書いた場合、`<span class="pkc-lead">` で wrap して見た目を出します(canonical は通常段落)。

`:quote:{attribution=X}` のような inline attribution を書いた場合、`<small class="pkc-attribution">— X</small>` で render します(canonical は block 形 `:::quote{author="X"}`)。

閉じ忘れ `:::quote{author="No Close"`(`}` 忘れ)も寛容に受けます。role 部分(`:::quote`)を opener として認識、attrs は drop、content は EOF まで(または次の opener まで)取り込みます。連続 `:::\n:::` も正しく独立 closer として認識します。行頭の tab や全角スペースも leading whitespace strip して認識します。

詳細仕様 / 設計議論は `docs/development/parser-recovery-spec.md` を参照してください。

### 12.9.6 PKC MD ↔ HTML 不変式(supreme invariant)

:::section{role=important}
PKC2 の最重要 invariant は **「PKC MD = Rendered HTML」** です。GFM MD / Word(docx) / PowerPoint(pptx) などは副次的な derived format で、本 invariant に従属します。

具体的に何を意味するかというと:**📋 PKC MD ボタンで copy したテキストを別の entry に貼り付けて再 render した結果が、元の entry の HTML と完全同一(deep-equal)になる** ということです。AST も deep-equal、round-trip 2 cycle で stable(完全な不動点)。
:::

これは「source markdown ≡ AST ≡ Rendered HTML の 3 表現は **完全に可換** で、どこから入っても同じ意味になる」という設計を表します。Word / PPT への変換、AI への AST 渡し、外部エディタとの相互運用、すべての downstream 処理が、この invariant を起点に組み立てられています。

実装上、この invariant を満たすために 2026-05-16 の PR-W24 wave で以下の正規化を行いました:

ruby は `{base|rt}` ではなく `[[ruby:base|rt]]` を canonical 形に採用しました(decompose と互換)。section break は `:::page-break` ではなく `+++`(Simple 形)を採用(round-trip 安定性のため)。`AstSpan` で class のみを持つものは L-6 Simple `:X:cls1,cls2:` 形を採用、id や key=value も持つものは Formal `:span:[X]{#id key=v}` 形を採用しました(両 path で decompose が同じ AST に戻る canonical)。AstFigure の figureKind=`figure`(default)は attrs に `kind=figure` を emit しません(re-parse で重複 attrs を起こすためです)。段落の align は `{align=X}` annotation ではなく行頭 `||` `|>` marker、indent は `{indent=N}` ではなく行頭 `__` marker を採用、AstBlank の count も `_N` marker で persist させます。これらは全て「PKC MD ↔ HTML を完全同一に保つ」ための canonical 形選択です。

### 12.9.7 完了済みと未実装

ここまで読んでいただいた記法のうち、v2.3.0 の Wave Z(2026-05-16 締め)時点で実装済のものを整理します。

`L-1 〜 L-9` の Simple 形(セクション区切り / ハイライト / ルビ / 圏点 / 引用 / コメント / 行頭 align / 簡易 inline / 図表 + 参照 / 空行マーカー / 段落字下げ)は **完全実装**、本章 §12.1〜§12.6 で詳しく解説しています。

`R-2A 〜 R-2H` の Formal 形(frontmatter document globals / quote citation / sup-sub / span / formal inline 4 種 / `:caption:` / auto-ref / paragraph align / section role / comment / break)も **完全実装**、本章 §12.7〜§12.9 で解説しました。

数式 `$X$` `$$X$$` の AST 化 + docx 視覚区別、脚注 `[^id]` の Word native(`FootnoteReferenceRun` + `Document.footnotes` API)、色ハイライト `==[color]X==` の 3 形対応はすべて 2026-05-16 までに着地済みです。

一方、**設計のみが保存されている**(未実装)のは主に 2 つあります。

1 つ目は **PKC Hint 機構**(`docs/development/pkc-hint-mechanism-2026-05-16.md`)。これは「PKC が parse / render 中に気づいた事象を user に統一 UI で伝える」共通機構で、現状散在している 5 種の hint(未定義変数の警告 / `_N` cap / orphan footnote / malformed `:::role{` / dangling `[@id]`)を統一 `AstHint` schema + 4 階層 opt-out にまとめます。詳細は [§15 PKC Hint 機構](./15_pkc_hint_機構.md) で解説しています。

2 つ目は **Code Block Ecosystem の Phase A-G**(`docs/development/notation-redesign-2026-05/06-code-block-ecosystem.md`)。これは ` ```tree ` ` ```dbschema ` ` ```query ` ` ```cards ` ` ```mermaid ` ` ```mindmap ` ` ```flow ` などの **15+ renderer を Plugin Registry architecture で開放する** 戦略です。`csv` と `html-render` は実装済ですが、他は将来 wave で 1 件ずつ。GFM の暴発を避けるため、§15.3.4 の「ブルーオーシャン戦略」(render-available 誘導)経由で opt-in する設計になっています。
