## 1. 🔴 まず私の誤りを訂正する

敵対的検証が私の報告した数字に 2 つの誤りを見つけた。**どちらも指摘が正しい。**

### 誤り 1: 百分率の取り違え

「残る 3.1 秒の 73% が `(program)`」と書いた。
**73.3% はプロファイラ有効時の 5,291 ms に対する比率**であって、
プロファイラ無効時の 3,110 ms に対する比率ではない。混ぜてはいけない。

さらに `(program)` は V8 CPU プロファイルの**受け皿バケット**で、
バンドルパースやレイアウトのほかに**プロファイラ自身のオーバーヘッド**も入る。
「5.9MB のバンドルパース + 15000 行のレイアウト」は **推定であって内訳の実測ではない**。

### 誤り 2: 「ストレージは 1.5%」を修正後にも適用した

1.5% は **修正前**(boot 22.9 秒)の比率である。修正後は:

| | 修正前 | 修正後(プロファイラ有効) |
|---|---|---|
| boot | 22,930 ms | 5,291 ms |
| IDB | 351 ms(**1.5%**) | 511 ms(**9.7%**) |

**IDB の絶対値は減っていない**(351 → 511 ms)。全体が縮んだので比率が上がった。
つまり「ストレージは 1.5% だから設計対象外」は**修正前の話**であり、
**これから何を設計するかの根拠には使えない**。

⚠ 私はこの誤った比率で「WAL / パーティション化は 1.5% への提案」と user に伝えた。
**正しくは「修正前は 1.5%、修正後は 9.7%、絶対値は横ばい」**である。
WAL の評価は §4 で数字を使わずに述べ直す。

## 2. 断面ごとの現状(8 本の調査で file:line 確定)

**全断面に共通する構造**: どの断面も必要な最小データは小さいのに、
`AppState.container` が単一の巨大オブジェクトなので全部を読んでいる。

| 断面 | 本当に必要な最小データ | いま読んでいるもの |
|---|---|---|
| **boot / TTI** | 可視行数ぶんの meta + structural relation + 開く 1 件の body | 全 body / 全 revision / 全 relation |
| **操作可能の種類** | ― | **段階的に操作可能にする仕組みが無い**。phase は 2 値 |
| **ランチャー** | 数十件の `{lid,title,icon,kind,group,order,url}` | 全 body / 全 45000 revision / 全 relation / 全 attachment body |
| **一覧/検索/ソート/tree/filer/quick-open** | **meta + relations だけで完全に成立** | 全 body |
| **保存追記** | 変更 entry 1 + revision 1 + 索引 1 件分 | **O(N+M)**(`marker.revOrder` = 全 revision id、layout 5 の core = 全 entry meta) |
| **削除 / ゴミ箱** | lid + 直前状態 / `(lid,title,archetype,deleted_at,rid)` | 全 M 走査 + 候補ごとに snapshot 本文を parse |
| **アダプタ 3 種** | key → 不透明値 | 「default が空か」を知るために container 全体 + 全 asset(**2026-07-25 に修正済**) |
| **可搬性(HTML/ZIP)** | write-only stream | base64 の往復 + 全量同時保持 |

### 設計を縛る既存の地雷(全案が踏む可能性がある)

- **`body === ''` が「未 hydrate」の sentinel**(`body-working-set.ts:59-61`)。
  「本当に空の本文」と構造的に区別できない
- **`persistence.ts:221` の `bodiesPending` guard が唯一の防護**。
  hydrate 未完で保存すると本文が空で焼き付く
- **FS 系は JSON 直列化可能な値のみ**。Blob を渡すと `{}` になり**無言でデータ消失**
- **StorageAdapter の seam 拡張は設計 doc の不変条件**(`opfs-storage-adapter-design-2026-06.md` §7)
- **bucket 横断トランザクションを表現する型が無い**(`storage-adapter.ts:108-132`)
- **tombstone を持たないのは明示された設計判断**(`container-ops.ts:12-19`)
- **ゴミ箱の実体 = revision 表の差集合**。revision を遅延させると**ゴミ箱が壊れる**
- **`bootReady` はテスト同期専用契約**。全 smoke spec が await している

## 3. 立てた 3 案

| 案 | 主題 | 規模 |
|---|---|---|
| **① Shell-First** | 実測に忠実。サイドバー仮想化 + 重量 dep の 2 段化 + boot に要る派生値を 1 レコードに materialize。ストレージ変更は 2 点だけ、**WAL は採らない** | L |
| **② HOT/WARM/COLD 三面** | user の WAL 案を最強化。segments bucket へ**冪等スナップショット WAL** を追記、idle にチェックポイントで既存 layout 5 へ編入、`containers` に**ブートマニフェスト 1 レコード**。**bucket も seam も DB_VERSION も増やさない** | XL |
| **③ Facet / Body 二層** | `Entry.body` を型から外し、**永続 facet プレーン(小・常駐・再導出可能)** と **body/revision プレーン(大・需要読み)** を別レコード・別型・別ライフサイクルに。`body===''` sentinel を撤廃 | XL |

### 3 軸判定 — 割れた

| 軸 | 勝者 |
|---|---|
| 実測との整合 | ① Shell-First(9/10) |
| 後方互換とデータ安全 | ② HOT/WARM/COLD(8/10) |
| 指令整合と着地可能性 | ① Shell-First(7/10) |

## 4. 🟢 3 案が一致した点(ここは裁定に足る)

判定 3 軸と 3 案が独立に同じ結論に達した点は、案の優劣と無関係に信頼できる。

1. **WAL は boot を速くしない。効くのは保存断面である。**
   WAL 案の設計者自身が「この案は実測 boot 22.9 秒に対する提案ではない」と冒頭で自認した。
   ただし **保存が本当に O(N+M) であることはコードで確定**しており、そこには効く
2. **「速い DB / 遅い DB」ではなく「meta+索引 / 本文」で切るべき。**
   一覧・検索・ソート・tree・filer・quick-open・ランチャーは **body を 1 バイトも必要としない**。
   分割の軸は媒体ではなくデータの種類である
3. **派生値は保存時に確定させ、boot で原文から再計算しない。**
   revision 件数 / task 進捗 / launcher tile / ゴミ箱行 / 被参照数 —
   いずれも「数十バイトの事実」のために本文と履歴を全部読んでいる。
   **`getRevisionCount` の O(N×M) はその最も極端な実例**で、既に修正済み
   (同一ハーネスで **27,201 → 936 ms**。⚠ 初版の「8.7 倍」は別ハーネス同士の
   比較で撤回済み ── `boot-cost-profile-2026-07-25.md` 冒頭の訂正ブロック参照)

### WAL 案の副産物(採否と無関係に価値がある指摘)

- `del()` が新 prefix を消さず孤児化する key 衛生の問題
- FS 系で `saveDiff` が取る経路の問題
- **`findLatestRevisionIdForLid`(`container-ops.ts:359-371`)と `removeEntry` の
  relations 全走査に、`getRevisionCount` と同じ罠がまだ生きている**
  (ただし前者は保存 1 回につき 1 度 = O(M) 1 回で、修正後プロファイルに現れていない。
  §6 の再計測で確認してから触る)

## 5. 🔴 敵対的検証 ── 3 案とも論破された

| 検証 | 判定 | 決め手 |
|---|---|---|
| **データ消失** | 論破 | ① の readiness T3「per-entry ゲート化」が、**コード自身が「これが唯一の防護」と書いているゲートを外す**。さらに **ShellIndex による T1 boot は revision を遅延させるが、revision には bodies のような遅延状態も保存ゲートも存在しない** ── 1 回の保存で**履歴とゴミ箱が消える**。`differential_save` 既定 ON はリポジトリ自身が実測で撤回した判断への逆行 |
| **効果が出ない** | 論破 | ①の主軸が立っている定量的前提(`(program)` 73%)が**再現しない**。§1 の誤りを突いた指摘。加えて「IDB 1.5% だからストレージを除外」という理屈を、**① 自身がストレージに対して犯している** |
| **着地しない** | 論破 | ① P0 の「`latestRevByLid` を同型 WeakMap で索引化」は**ヒット率が構造的に 0%** になり現状より遅くなる。「バンドル 2 段化は `inlineDynamicImports` を外すだけ」は**事実として誤り**(当該 flag は現行 vite で既に無視されており、lib/IIFE モードでは code splitting が構造的に不可能)。サイドバー仮想化は「既存 memo の上に載せる」追加工事ではなく、**DOM を順序の正本として読む機構が 4 つあり全部作り直し**になる |

**⇒ どの案もこのままでは実装に進めない。**

特に **①の「サイドバー仮想化」は本命に見えたが、DOM を順序の正本として読む機構が
4 つある**という指摘が効いている。これは「描画層をやればいい」という私の見立てが
甘かったことを意味する。

## 6. ⇒ 次にやるべきこと(裁定を仰ぐ点)

### 先に測り直す(推奨)

3 案とも「修正後の boot の内訳」の上に立っているが、**その内訳は争われている**(§1)。
`(program)` を分解しないまま XL の再設計に進むのは、
本セッションで繰り返し戒めてきた「手法を固めずに数字を出す」の再演になる。

**測るべきもの:**

1. `(program)` の分解 ── Performance timeline / longtask attribution で
   「バンドルのパース」「スタイル計算」「レイアウト」「paint」に割る
2. **asset を含む規模での再測**。本セッションの計測は全て **asset 0**。
   user の「500MB 超」は asset 主体で、そこは P1(Blob 化)の領分
3. 保存断面の実測 ── ここだけは **O(N+M) がコードで確定**しており、
   WAL / 索引差分化の効果を事前に見積もれる

### 裁定していただきたいこと

- **A. 測り直してから設計を確定するか、いま 3 案のどれかを土台に進めるか**
- **B. 保存断面(O(N+M))だけ先に着地させるか** ──
  ここは 3 案が一致し、コードで確定していて、boot と独立に進められる
- **C. `body === ''` sentinel の撤廃**(③ の唯一の純粋な「削る」)を
  単独で先に着地させるか ── データ消失の温床を 1 つ減らせる

私の推奨は **B → 測り直し → 設計確定** の順。理由は、B が
「3 案一致 + コードで確定 + boot と独立」の 3 条件を満たす唯一の項目だからである。
