# 保存形式の書込 I/O 実測(2026-07-25)

> user 指示(2026-07-25):「ベンチして根拠ありで正しく着地しましょう」

処遇 doc [`lazy-entry-bodies-disposition-2026-07-25.md`](./lazy-entry-bodies-disposition-2026-07-25.md) §6 が
user 裁定待ちにしていた問い ──
**「`differential_save` の保存形式を split v1 から layout 5 へ一本化すべきか」** に、実測で答える。

ハーネス: `tests/bench/storage-write-io.mjs`(本番コード経路 = `dist/pkc2.html` を実 UI 操作で駆動)

---

## 結論

**一本化しない。** 加えて、**私が処遇 doc で「する」を推したのは撤回する** ── 実測が支持しなかった。

さらに、当初の問いより重い発見があった:

> **差分保存の per-edit 書込削減は約 -25% どまりで、設計が謳う O(1) ではない。**
> split v1 も layout 5 も、**毎保存で O(N+M) のレコードを書いている**(コードで確認済、§4)。

## 1. 測定条件

| | |
|---|---|
| fixture | 5000 entries / **15000 revisions** / assets 0 / 21.1 MB |
| 指標 | `/proc/diskstats` の実デバイス書込(sectors written × 512B、`sync` 済) |
| 反復 | 3 回(独立プロファイル・独立ブラウザ) |
| 編集 | 1 編集 = エントリ選択 → 編集開始 → 本文に 1 文字 → 確定。text エントリのみ |

腕:

| 腕 | flags | 保存経路 |
|---|---|---|
| Z 床 | 両 OFF | 編集を 1 回もしない(放置時のノイズ) |
| **Y 対照群** | 両 OFF | 同じ操作をして **CANCEL_EDIT で抜ける** = 保存だけ起きない |
| A | 両 OFF | `save()` = inline 全件 |
| B | diff のみ | `saveDiff()` targetLayout 1 = **split v1** |
| C | diff + lazy | `saveDiff()` targetLayout 5 = **segments** |

**保存に帰せられる書込 = その腕 − Y。**

### ⚠ Y が本ベンチの肝(最初は間違えた)

当初は Z(ブラウザ放置)だけを対照群にして「1 編集あたり 3.2MB」と出した。
ところが **コンテナを 1/10(4.8MB → 500KB)にしても 4.1MB と出た** ──
測れていたのは保存ではなく **操作そのものがブラウザに書かせる分**だった。

`CANCEL_EDIT` が `SAVE_TRIGGERS`(`persistence.ts:48-79`)に含まれないことを使い、
**クリック・打鍵・phase 遷移・再描画をすべて同じにして保存だけ起きない**腕に作り直した。
Y の実測は 1000 件 1124 KB / 5000 件 1209 KB と **コンテナサイズに依存しない** ので、
操作オーバーヘッドとして正しく分離できている。

計測手法自体も先に検証した:放置 0.7MB に対し 20MB 書込 → 19.3MB、60MB → 54.4MB
(信号がノイズの 15〜40 倍・線形)。

対照群 Y: 1209 / 1329 / 1183 KB → **中央値 1209 KB / 操作**(これは保存ではない)

| 腕 | 保存書込 / 編集 | レンジ | 変換 1 回 | 最終使用量 | **boot 中央値** | boot レンジ |

| | 保存書込 | 使用量 | 変換 | boot |

| C layout 5 | **-25%** | **×0.60** | **×0.92** | **+84 〜 +109%** |

## 2-b. スケール掃引(2026-07-25 追加。user 指摘「スケールもテストすべきだった」)

初版は **5000 entries の 1 点だけ**で結論を出していた。#967 の user 指示は
「500MB 超が当たり前」であり、1 点では **boot ペナルティが規模とともに
拡大するのか縮小するのか分からない**。3 点で測り直した(各 EDITS=4)。

| 規模(entries / revisions / MB) | | A inline | B split v1 | C layout 5 |
|---|---|---|---|---|
| **1000 / 3000 / 5MB** | boot | 616 ms | 747 ms(+21%) | 797 ms(**+29%**) |
| | 使用量 | 1.4 MB | 2.5 MB | **2.1 MB(×1.5 — inline より悪い)** |
| | 変換 | 15.3 MB | 14.4 MB | 14.5 MB |
| **5000 / 15000 / 25MB** | boot | 3303 ms | 3926 ms(+19%) | 6880 ms(**+108%**) |
| | 使用量 | 6.7 MB | 10.1 MB | **4.1 MB(×0.61)** |
| | 変換 | 21.2 MB | **55.9 MB** | 19.1 MB |
| **15000 / 45000 / 78MB** | boot | **27201 ms** | 29300 ms(+8%) | **49937 ms(+84%)** |
| | 使用量 | 19.9 MB | 29.5 MB | **11.6 MB(×0.58)** |
| | 変換 | 31.3 MB | **145.3 MB(×4.6)** | 24.8 MB |

### 分かったこと

1. **layout 5 の boot ペナルティは規模で消えない。** +29% → +108% → +84%。
   どの規模でも inline に負ける。「大規模なら逆転する」という期待は**否定された**
2. **layout 5 の容量優位は規模で初めて現れる。** 1000 件では **inline より 1.5 倍大きい**。
   0.6 倍になるのは 5000 件以上。小規模で ON にすると損しかしない
3. **split v1 の変換コストが規模で破綻する。** 14.4 → 55.9 → **145.3 MB**(inline の 4.6 倍)。
   一方 layout 5 の変換は最も安く、規模でもほぼ伸びない(14.5 → 19.1 → 24.8 MB)
4. 🔴 **既定(inline)の boot が 78MB の本文・履歴で 27 秒。** レイアウト選択より
   こちらのほうがはるかに大きい問題である(§4 の O(N+M) と同根の可能性が高い)

### この掃引で無効だったもの(正直に記録)

**15000 件の per-edit 書込は測れなかった。** 対照群 Y が 41.1 MB に膨れ、
B/C の定常書込(30.6 / 31.9 MB)を上回ったため、差し引きが負になった。
ハーネスのガードが `⛔ 上の警告がある限り、この実行の数字を結論に使ってはならない`
を出して自動的に無効化している。

さらに、**per-edit 書込の絶対値は測定条件に敏感**である。同じ 5000 件でも
EDITS=6 では B が -26%、EDITS=4 では -63% と出た。差し引き前の Y が
条件で動くため、**per-edit 書込は「差分保存 < inline」という向きだけが信頼でき、
倍率は信頼できない**。B と C の優劣は依然として分解できない。

### 何が固い所見で、何が弱いか

| 指標 | 測り方 | 信頼度 |
|---|---|---|
| **boot** | 直接測定(差し引きなし)、A は ±0.6% | 🟢 **固い**。A < B < C はどの規模でも一貫 |
| **使用量** | 直接測定 | 🟢 **固い** |
| **変換コスト** | 直接測定 | 🟢 **固い** |
| per-edit 書込 | Y との差し引き | 🟡 **向きのみ**。倍率は条件依存、B/C 間は分解不能 |

## 3. 一本化しない理由

### 🔴 layout 5 は boot をほぼ倍にする ── #958 と同じ軸

C の boot は 3 回とも A の **1.8〜2.1 倍**。しかも **A 自身が ±0.6% で極めて安定**しており、
これはノイズではない。

#958(差分保存の既定 ON 撤回)の理由はまさに boot だった。
**boot を倍にする形式を既定にはできない。** 使用量が 0.6 倍になっても、
それは既定を変える理由にならない ── 起動は全 user が毎回通る経路で、
storage 使用量は困っている人だけの問題である。

機構の推定: layout 5 の boot は **revision segments を全件 gunzip する**
(`idb-store.ts:926-928` は `skipBodies` に関係なく `loadRevSegments` を実行する)。
15000 revisions を 21 segment に gzip して持つぶん、伸長 CPU が boot に乗る。

### layout 5 に利点が無いわけではない

- **使用量 0.6 倍**(3.4 MB 対 5.7 MB)── gzip は確かに効いている
- **変換コスト最小**(18.7 MB。split v1 は 49.7 MB = **2.4 倍**)
- per-edit 書込は split v1 と実質同じ(2898 対 2853、C 自身の振れ幅 ±24% の内側)

⇒ **storage 逼迫で困っている人向けの opt-in としては引き続き妥当。既定にはしない。**

### split v1 も一本化先にならない

B は boot +8% と軽微だが、**使用量 1.6 倍・変換コスト 2.4 倍**。
per-edit 書込の -26% と引き換えにこれを全 user に配る根拠は無い。

## 4. より重い発見 ── 差分保存は O(1) ではない

**「差分保存は書込を変更分 O(1) にする」という前提が、この規模で成り立っていない。**

実測: A 3851 → B 2853 KB(**-26%**)。O(1) なら KB オーダーのはずである。

コードで機構を確認した(`idb-store.ts` の marker / core 構築):

```
const marker: SplitMarker = {
  entryOrder: wantSplitBodies ? [] : container.entries.map((e) => e.lid),
  revOrder: container.revisions.map((r) => r.id),      // ← 15000 件を毎保存
};
const core: StoredContainerRecord = {
  ...
  entries: wantSplitBodies
    ? container.entries.map((e) => (e.body === '' ? e : { ...e, body: '' }))  // ← 全 5000 件を毎保存
    : [],
  ...
};
```

- **split v1**: marker に `entryOrder`(5000 lid)+ `revOrder`(15000 id)= **O(N+M) を毎保存**
- **layout 5**: `entryOrder` は空だが `revOrder` は **O(M) を毎保存**、さらに core record に
  **body を落とした全 5000 entry = O(N) を毎保存**

差分になっているのは entry / revision の **本体**だけで、**索引と順序リストは毎回全書き**である。
N・M が大きいほどこの固定費が支配し、差分の利得を食う。

**改善の余地はここにある**(順序リストの差分化 / 索引の分割)。
保存形式の切替よりこちらのほうが効果が大きい可能性が高い。これは別 issue。

## 5. 本測定の限界(結論に効くもの)

1. **高速ディスク上の測定**(virtio / ext4、`/proc/diskstats` の `vda`)。
   #958 の user 報告は **遅いストレージ**の話だった。gunzip の CPU が boot 増の主因なら、
   I/O が支配的な遅いディスクでは順位が変わりうる。**遅いストレージでの再測は未実施**
2. **asset 0 の fixture なので、本ベンチは「本文・履歴プレーン」しか測っていない。**
   500MB 級の実運用は asset 主体であり、そちらは P1(Blob 化)の領分。
   **asset を含む規模での通し計測は未実施**
3. **編集は 6 回**(掃引は 4 回)。debounce(300ms)より十分あけて 1 編集 = 1 保存にしているが、
   5000 件では保存自体が長引く場合があり、一部が合流した可能性は排除できない。
   合流は保存回数を減らすので **per-edit を過小評価する方向**に働き、
   最も保存が重い A に最も強く効く ⇒ 「A が最も重い」という結論には安全側
4. **C の振れ幅が大きい**(±24%)。segment の compaction が走る回か否かで変わるため。
   C の per-edit 書込を B と厳密に比べるだけの分解能は無い(順位付けはしていない)
5. **per-edit 書込は測定条件に敏感**(§2-b)。向きは信頼できるが倍率は信頼できない。
   15000 件では対照群 Y に埋もれて測定不能になり、ハーネスが自動的に無効化した

## 6. 着地

| 項目 | 判断 |
|---|---|
| `differential_save` を layout 5 へ一本化 | **しない**(boot ほぼ倍) |
| `differential_save` の既定 | **OFF 据え置き**(#958 の判断は追認された) |
| `lazy_entry_bodies` の既定 | **OFF 据え置き**(診察 doc の結論を追認) |
| `lazy_entry_bodies` の廃止 | **しない**。storage 逼迫向けの opt-in として利点が実証された(使用量 0.6 倍・変換コスト最小) |
| マニュアルの記述 | **実測のトレードオフに書き換える**(「起動が速くなる」ではなく「保存領域は減るが起動は遅くなる」)。**小規模(〜1000 件)では容量も増える**ので、opt-in の条件は「大きくて、かつ保存領域が逼迫しているとき」 |
| 次にやるべき perf 改善 | 🔴 **既定 boot が 78MB で 27 秒**(§2-b)。レイアウト選択より桁違いに大きい。原因候補は §4 の O(N+M) 毎保存と同根 ── **ここを最優先にすべき** |

### 改修全体の位置づけ(user 問い「この改修は無駄だったのか」2026-07-25)

**無駄ではないが、効いた部分と効いていない部分を分けて記録する必要がある。**

| 段階 | 内容 | 状態 | 実測 |
|---|---|---|---|
| **P1** | asset を base64 → **Blob** | ✅ landed・flag なし・全 user | **300MB cold 11,076ms → 16ms**、ヒープ +293MB → ±0(redesign §A.1 の A 対 E) |
| **P2** | segments(本文・履歴の分割 gzip) | opt-in・既定 OFF | 容量 0.58〜0.61 倍(5000 件以上)/ **boot +29〜108%** |

⚠ **`session-handoff-2026-07-24.md:12` は「P2 セグメントログ … 実測: cold 11s → 16ms 級」と
書いているが、その 11s → 16ms は P1(asset Blob 化)の数字である。**
2 つを混ぜて記録したことが、本セッションの誤解の出発点になった。

そして **segments は 500MB 問題に触っていない** ── redesign §A.7 が
「**メディア(Blob)はパック対象外(圧縮 1.0×・コピー I/O が増えるだけ)**」と明記している。
user が挙げた「500MB 超」「4MB のエントリ」は asset 主体の問題であり、
**それを解いたのは P1** である。segments が触るのは本文と履歴という、はるかに小さいスライス。

### エンジン選定は妥当だったか(user 問い「wasm-sqlite の方が良かったのでは」)

**実測で落とされている**(redesign §A.1、300MB 実ディスク、単位 ms):

| 構成 | 投入 | cold start | 1件読み | 10件読み | 追記10件 |
|---|---|---|---|---|---|
| D SQLite WASM(OPFS SAHPool・BLOB) | 2,295 | 22 | 7.1 | 156 | 200 |
| **E IDB + Blob(採用)** | 2,281 | **16** | **0.8** | **6** | 197 |

書込はほぼ互角、**読みが 9〜26 倍遅い**。加えて bytes が WASM リニアメモリを通るため
**+246MB 常駐**(sql.js 計測)、read パスの syscall 60 倍、単一 HTML に +1MB の WASM。
しかもこの結論は「D は壊滅的に遅い」という当初判断を
**incognito アーティファクトとして撤回した上で**出されている(§A.1)。エンジン選定は妥当。

**ただし批判が当たる先が別にある。** IDB の上に積んだ自前機構 ──
セグメントログ / gzip パック / compaction ヒューリスティック / body 索引 /
順序リスト / layout 1〜5 の相互互換 ── は **DB エンジンがくれるものの再実装**であり、
本ベンチはその自前層が **毎保存で O(N+M) を書いている**(§4)ことを見つけた。
まともなストレージエンジンなら犯さない類のミスである。

> **一番効いた変更(base64 → Blob)は一番単純だった。複雑な部分(segments)はまだ payoff が出ていない。**

「単一 HTML」は user 由来の製品制約なので自前化そのものは避けられないが、
**その制約の下でどこまで作り込むか**の判断には順序の問題があった ──
#967 が user 裁定待ちのまま P2 の実装だけが先に landed している。
**P1 の効果を実測してから P2 の要否を判断すべきだった。**

処遇 doc の推奨のうち **§5「畳むべきは split v1 の書き手ではないか」と §6 の「一本化する」推しは、
本実測により取り下げる**。split v1 は per-edit 書込では最良で、boot も +8% にとどまる。
