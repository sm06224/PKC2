# 階層ストレージとレンダリングキャッシュ ── ティア設計(実装しない・user 裁定待ち)

> 🔴 **user 提起(2026-07-28)。本 doc の出発点**
>
> 「**SQLite を使うにしろ使わないにしろメモリにインデックスする分は常は少なくていい**はず、
> それは Postgres などの DB のアーキテクチャ的にも正しい。
> **実体化にかかる部分やソーティングのみに関わるインデックス**を持てばいい話のはず、と私は考えています。
> **DOM 再現についても、参照のみの場合は前回のレンダリング結果を使いまわせる**はず、
> つまり**ファストラインとして圧縮したレンダリング結果をストレージにキャッシング**して、
> キャッシュヒットに期待するのも十分にアリではないでしょうか?
> さらに**ユーザーのモニタや描画エリアサイズに適したレンダリングを行い低解像度キャッシング**するなどの方法もあるはず。
> つまり **PKC はティアレベルを持つ階層ストレージを必要とする段に入った**と考えるべき。
> **フォールバック経路を含めると複雑化する**が、**ストレージとキャッシュ層のアーキテクチャを固める必要がある**」

以降、この 4 つを **①常駐 index / ②描画キャッシュ / ③解像度適応 / ④ティア階層** と呼ぶ。

## 0. 先に測った ── 4 案の賞金はいくらか

設計を語る前に計器を置いた。**どれも「やってみないと分からない」ではなく数字が出る問いだった**ので、
先に測ってから設計している。新設した harness:

- `tests/bench/entry-meta-residency.mjs` ── entry メタ配列の常駐が N でどう伸びるか
- `tests/bench/center-render-repeat.mjs` ── 同じ entry を開き直したとき描画をやり直しているか

### 0-a. ①の賞金は**小さい**(が、棄却理由にはしない)

本文を空にした container を N だけ変えて seed し、強制 GC の後に JS heap を読む(2 回目起動・各 3 回の中央値):

| N | JS heap | サイドバー DOM 行 | nodes | listeners |
|---|---|---|---|---|
| 1,000 | 5.8 MB | 34 | 712 | 145 |
| 10,000 | 8.2 MB | 34 | 712 | 145 |
| 50,000 | 18.3 MB | 34 | 712 | 145 |

**傾き = 1 entry あたり 266 バイト**。10 万 entry でも**メタ配列は 25MB 程度**である。
P4b 後の body-heavy container の app 取り分が USS +164.7MB だったことと比べると、桁が 1 つ小さい。

⚠ **これを「効果が小さいからやらない」の根拠にはしない**(user 指示③)。ここで確定したのは
**「①のメモリ動機は弱い」**であって、①そのものの棄却ではない。①には**別の動機**があり得る
── 毎描画で全 N を sort / filter / tree 構築している **CPU 側**である。そちらは未計測なので
**計測タスクとして §9 に残す**。数字が出るまで①の優先度は決めない。

**副産物として重要な 2 つの事実**:
- **DOM 行 / nodes が N に依らず一定** ── S6(サイドバー窓化・既定 ON)が効いている
- **listeners が 145 で一定** ── ActionBinder が委譲(`data-pkc-action`)で張っているので、
  **描画結果を後から差し戻しても listener を張り直す必要がない**。②の実現可能性の前提が成立している

### 0-b. ②の前提は**成立する**。ただし②単独では 1/3 しか買えない

本文 120KB の text entry を 2 件作り、A↔B を交互に 5 往復して「選択 → center pane 描画完了」の
**long task**(メインスレッド占有)を測った:

| | wall | long task |
|---|---|---|
| 初回 2 回の平均 | 2,076 ms | **1,915 ms** |
| 3 往復目以降の平均 | 2,243 ms | **2,061 ms** |

**同じ entry を開き直しても速くならない ── 再利用が 1 ミリも効いていない。**
user の見立て「参照のみの場合は前回のレンダリング結果を使いまわせるはず」は**そのとおり**で、
今は毎回まるごと描き直している。

そこで「キャッシュが当たったら何秒で済むのか」の**下限**を測った。描画済み HTML を取り出し、
gzip → 展開 → `innerHTML` で作り直す時間:

| | 値 |
|---|---|
| 生 HTML | 1,544 KB(**21,416 要素**) |
| gzip 後 | **56.6 KB**(原文 120KB の 47%) |
| gzip 圧縮 | 14 ms(保存側) |
| gzip 展開 | 5〜6 ms(読み出し側) |
| `innerHTML` で再構築 | **1,291〜1,447 ms** |

**キャッシュヒットの下限 ≒ 展開 6ms + 再構築 1,291ms = 約 1,300 ms。**
現行の約 2,000 ms に対して **買えるのは 700ms 程度(約 35%)** にすぎない。

🔴 **理由: 支配的なのは markdown → HTML の変換ではなく、HTML → DOM の構築である。**
120KB の本文が **21,416 要素**になり、その構築だけで 1.3 秒かかる。
キャッシュは変換を消すが、**要素を作る仕事は消さない**。

### 0-c. ④と組ませると桁が変わる ── **ここが本 doc の核心**

同じ HTML を「先頭から一部だけ」流し込んだときの時間(ブロック境界で切り、部分木の要素数で割った):

| 挿入量 | ブロック | 要素 | `innerHTML` |
|---|---|---|---|
| 10% | 38 | 2,131 | **128 ms** |
| 25% | 94 | 5,267 | 339 ms |
| 50% | 188 | 10,531 | 613 ms |
| 100% | 375 | 21,416 | 1,291 ms |

**きれいに線形**(約 60 µs / 要素)。つまり center pane も**サイドバーと同じ理屈で窓化できる**。

4 つの経路を並べると:

| 経路 | 見積り | 現行比 |
|---|---|---|
| 現行(毎回まるごと描き直し) | ~2,000 ms | — |
| ②のみ(全量キャッシュ + 全量差し戻し) | ~1,300 ms | −35% |
| ④のみ(窓化・変換は毎回) | 変換 ~700ms + 挿入 128ms ≒ **~830 ms** | −59% |
| **②+④(ブロック単位キャッシュ + 窓化)** | 展開 6ms + 挿入 128ms ≒ **~135 ms** | **−93%** |

🔑 **②と④は掛け算になる。どちらか片方では足りない。**
そして**順序がある** ── ④(窓化)を先にやると単独で −59% が入り、その上に②を載せると −93% になる。
逆順(②を先)だと −35% で止まり、しかも次の④で作った資産の作り直しになる。

🔴 **この事実は設計に 1 つ硬い制約を課す。キャッシュは「1 本の HTML 文字列」で持ってはいけない。**
窓化して一部だけ差し込むには**ブロック単位で取り出せる**必要があり、
1 本の文字列だと切り出すために全部 parse する羽目になって**挿入と同じ額を払う**(= ②のみの経路に落ちる)。
**キャッシュの単位はブロックであり、ブロックごとの長さ(spacer 用の高さ)を併せ持つ。**
これはサイドバー窓化(L3-S3〜S5)で `data-pkc-row-count` + spacer が果たした役割と同型である。

### 0-d. 幸い、ブロック境界の機構は**既にある**

`src/features/ast/render-html.ts` の `renderAstToHtml()` は AST のブロックを 1 個ずつ HTML 化して
join しているだけで、`sourceLineAnchors` を有効にすると各ブロックに
`data-pkc-source-line` が付く(`render-html.ts:68`、Split View preview が既に使っている)。
**join する前の配列を返せるようにする**のが②+④の入口であり、新機構ではない。

## 1. ティア定義

「所有者・寿命・破棄条件」を持たない常駐物を作らない。**これは B13 / B18 / B9 / B12 で実際に踏んだ
事故がすべて「所有者と寿命が無かった」型だったことによる。**

| ティア | 媒体 | 中身 | 所有者 | 寿命 / 破棄条件 | 目安サイズ |
|---|---|---|---|---|---|
| **T0 hot** | JS heap + DOM | 可視ブロックの DOM / サイドバー窓の行 / 選択中 entry の本文 | renderer | 窓が動いた瞬間・選択が変わった瞬間 | 窓ぶん(N 非依存) |
| **T1 warm** | JS heap(上限つき LRU) | 本文 working set(P4b、200 万文字)/ 直近 entry の**ブロック HTML 配列** | working set | 上限超過で古い順・選択/編集中は対象外 | 上限で決まる |
| **T2 durable** | sqlite 行 / OPFS / IDB | core record の行 + **render cache 表(ブロック単位・gzip)** + asset Blob + 低解像度ラスタ | storage adapter | **quota 逼迫時に cache から先に捨てる**。core より先 | cache は本文の約 50%(実測 47%) |
| **T3 cold** | 交換形式 | export ZIP / pkc-data 埋め込み | user 操作 | user が消すまで | — |

**T2 の cache は「捨てられること」が設計要件**である。捨てて困るものを入れてはならない
── 入れた瞬間にそれは cache ではなく正本になり、⑦(双方向互換)と S1〜S4(静かなデータ喪失)の
両方に穴が開く。

## 2. 常駐集合の定義(①への回答)

**T0 + T1 に載ってよいものの閉じたリスト**:

1. 選択中 entry の本文(1 件)
2. 直近に見た本文(上限 200 万文字の LRU。P4b で実装済み)
3. サイドバーの窓に入っている行のメタ(S6 で実装済み)
4. 直近に見た entry のブロック HTML 配列(**新規・上限つき**)
5. 並べ替え / 絞り込みに必要な列

**5 が①の核心**であり、ここだけが未決である。現状は `AppState.container` に**全件のメタが載っている**
(`app-state.ts:105` の `container: Container | null`)。これは **Invariant 4「Container is source of
truth」**の直接の帰結であって、バグではなく設計である。

user 提案の「実体化とソートに要るぶんだけ」を厳密にやるなら、並べ替えは SQL 側
(`ORDER BY … LIMIT … OFFSET`。索引は B3 で 6 本入れてある)に降ろし、heap には窓ぶんしか置かない。
**それは Invariant 4 の再解釈を要求する** ── §10 の裁定事項 1。

⚠ ただし §0-a のとおり**メモリ動機は 10 万 entry で 25MB** と弱い。
やるなら動機は CPU(毎描画の O(N))であるべきで、**その数字はまだ無い**。

## 3. レンダリングキャッシュ(②への回答)

### 3-a. 効く対象と効かない対象を分ける

| 対象 | キャッシュ | 理由 |
|---|---|---|
| text / textlog の markdown 本文 | ✅ **主戦場** | 出力が (body, flags, theme, markup 版) の純関数。実測 −93% の余地 |
| todo / form / folder の body | △ 小さい | 元々ブロック数が少なく、賞金が無い |
| spreadsheet | ❌ | セル編集で局所更新する機構が別にある。キャッシュは二重管理になる |
| mermaid / chart | ③ の領域 | SVG / canvas は HTML キャッシュではなく**ラスタ**で扱う(§4) |
| 添付プレビュー / 画像 | ③ の領域 | Blob と ObjectURL の所有権が絡む。HTML には入れない |

### 3-b. キー

`(container_id, lid, body_hash, markup_version, flags_digest, theme)`

- `body_hash` ── 本文が 1 文字でも変われば別物。**内容ハッシュであり updated_at ではない**
  (時刻キーは「変わっていないのに無効化」と「変わったのに当たる」の両方を起こす)
- `markup_version` ── markdown 方言のビルド識別子。**ビルドが変わったら全無効化**。
  これが無いと、新しい記法を足したビルドで古い HTML が当たり続ける
- `flags_digest` / `theme` ── 描画に効く flag(見出し番号・折りたたみ等)と配色

### 3-c. 保存形

**ブロックの配列**で持つ(§0-c の制約)。1 ブロック = `{ index, html, srcLine, heightHint }`。
`heightHint` は spacer 用で、サイドバー窓化の `measureUnitRowHeight` と同じ役割
── ただし本文ブロックは**高さが一様でない**ので、行高の中央値では代用できない。
**実測した高さをブロックごとに記録し、未測定は保守的な推定値**にする(サイドバーより難しい点)。

⚠ `content-visibility: auto` の未表示要素は**嘘の高さを返す**(サイドバーで実測 39px vs 真値 24.91px)。
高さの記録はこの罠を踏む位置にあるので、**測る対象は必ず「今 viewport に入っているブロック」**にする。

### 3-d. 置き場所

🔴 **`containers` object store に別キーで入れてはならない。**
#1022 のサイドカー事故(`__rel__:` / `__order__:`)と同型になる ── 旧ビルドが store を列挙したときに
**キャッシュが幽霊 container として一覧に出る**。**専用の object store / 専用の sqlite 表**に置く。

## 4. 解像度適応(③への回答)

対象は**ラスタ化できるもの**に限る:

| 対象 | 今 | 提案 |
|---|---|---|
| 画像添付 | 原寸 Blob → CSS で縮小 | 表示領域 × devicePixelRatio のサムネイルを T2 に持つ |
| contact sheet / book-base のサムネ | 同上 | 同上(一覧は特に効く) |
| mermaid | SVG を DOM に展開(**1 枚で renderer +6.9MB** の実測) | 表示サイズでラスタ化して T2 に置き、SVG は捨てる |
| chart.js | canvas | 静止時はラスタ、操作時に再生成 |
| markdown 本文 | — | **対象外**(テキストは解像度非依存) |

⚠ mermaid のラスタ化は**テキスト選択と拡大の劣化**と引き換えである。
拡大・ウィンドウリサイズで再生成する経路が要る。**これは裁定事項 3**。

## 5. フォールバック(user 提起④「フォールバック経路を含めると複雑化する」)

**複雑化の大半は「キャッシュが無かったらどうするか」ではなく「キャッシュがあるのに信じてよいか」である。**
前者は 1 経路(素直に描く)で済み、後者が分岐を生む。だから**キャッシュを一切信用しない既定**を作る:

| 事象 | 挙動 |
|---|---|
| ミス | 通常描画。**常に成立する**(キャッシュは純粋な派生物) |
| 復号 / parse 失敗 | 破棄して通常描画。⚠ **例外を握って黙らせない** ── `?pkc-debug=render-cache` で可視化 |
| キー不一致(ビルド更新・flag 変更) | ミスと同じ |
| quota 超過 | **T2 の cache から先に捨てる**。core record より必ず先 |
| OPFS 不可 | 既存 `storage-adapter` の seam で IDB へ。cache も同じ経路に乗る |
| readonly container | T2 に書かない(T1 のみ) |
| embed(iframe) | T2 を使わない |
| 旧ビルド | cache 表を知らない。**core record に混ざっていないので何も見えない**(§6) |

## 6. 双方向互換の判定表(Invariant 5)

**「この変更を知らない読み手が core record だけを読んだら何が見えるか」**:

| 読み手 | 見えるもの | 判定 |
|---|---|---|
| 新ビルド → 旧データ | cache が無いだけ。全部読める | ✅ |
| **旧ビルド → 新データ(core record)** | **今日とまったく同じ**。cache は別 store / 別表にあり core に 1 バイトも混ざらない | ✅ |
| 旧ビルドが store を列挙 | **cache を別 object store に置く限り見えない**。⚠ 同じ store に別キーで置くと幽霊 container として出る(#1022 と同型) | 設計制約 |
| 旧ビルドが保存 | cache を消すかもしれない。**消えても正しい**(派生物) | ✅ |
| 交換形式(export ZIP / pkc-data) | cache を**含めない**。派生物を交換形式に入れない | ✅ |

## 7. 段階(各段階が単独で着地し、単独で計測できる)

賞金の大きい順ではなく、**依存の順**に積む(§0-c の「④が先」)。

| 段階 | 内容 | 単独の賞金 |
|---|---|---|
| **C0** | 本 doc の裁定 | — |
| **C1** | 計器: center pane の long task / ブロック数 / (後に)hit 率。`center-render-repeat.mjs` を製品計器に格上げ | 0(ただし以降すべての前提) |
| **C2** | `renderAstToHtml` を**ブロック配列**で返せるようにする(join を呼び出し側へ)。**挙動不変の前工事** | 0(L3-S2 と同じ性格 ── C3 を断念しても資産が残る) |
| **C3** | **center pane のブロック窓化**(キャッシュ無し) | 2,000 → ~830 ms(**−59%**) |
| **C4** | ブロック単位 render cache を **T1(メモリ)** に | ~830 → ~135 ms(**合計 −93%**) |
| **C5** | cache を **T2(永続)** へ。セッション跨ぎの初回表示 | 未計測(§9) |
| **C6** | ③ 解像度適応ラスタ(mermaid / 画像 / contact sheet) | mermaid 1 枚 −6.9MB が上限 |
| **C7** | ① 常駐 index の縮小 | **CPU 計測の結果しだい**(裁定 1) |

**C3 が単独で最大**である。C4 以降を全部やらなくても、C2+C3 だけで現行の 6 割が消える。

## 8. 採らないもの

- **center pane 全体を 1 本の HTML としてキャッシュする** ── 採らない。§0-c の実測で
  **−35% で頭打ち**になり、しかもブロック窓化と両立しない形になる。方向ごと否定される案
- **キャッシュを core record に同居させる** ── 採らない。⑦ に触れる(#1022 と同型)
- **markdown 本文の低解像度化** ── 採らない。テキストは解像度非依存で、意味がない

⚠ **「効果が小さい」を理由に落としたものは 1 つも無い**(user 指示③)。
効果が不明なものは §9 の計測タスクに送っている。

## 10. user 裁定が要る点

1. 🔴 **Invariant 4 の再解釈**(①の前提)。
   現在「Container is source of truth」= 全件メタが heap に常駐。
   これを「**storage が正本、heap は窓**」へ変えるか。
   - **推奨: いま決めない**。メモリ動機は 25MB / 10 万 entry と弱く、CPU 動機は未計測。
     §9 の O(N) 計測を先に行い、数字を見てから決める(棄却ではなく保留)
2. **render cache をどこまで持つか**。T1(セッション内)で止めるか、T2(永続)まで行くか。
   - **推奨: C4(T1)までを先に着地させ、C5(T2)は hit 率の実測を見てから**。
     T2 は quota・破損・旧ビルドのフォールバックを増やすので、賞金を確認してから払う
3. **mermaid をラスタ化してよいか**(③)。テキスト選択と拡大が劣化する。
   - **推奨: 既定は SVG のまま、opt-in のラスタ化**。劣化が user に見える変更なので既定は変えない
4. **cache の置き場所**: 専用 sqlite 表 / 専用 IDB object store / OPFS ファイル。
   - **推奨: 専用 sqlite 表**(sqlite backend 時)+ 専用 IDB object store(IDB 時)。
     §6 のとおり `containers` store への相乗りは禁止
5. **この doc の段階を、いまの `dev/storage-sqlite` に積むか、別ブランチにするか**。
   - **推奨: 別レーン**。storage 移行(P2〜P5)と render cache は依存が無く、
     同じブランチに積むと 1 PR が高コスト化して着地しなくなる(50 PR 一本 stack の再演)
