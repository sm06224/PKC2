# 階層ストレージとレンダリングキャッシュ ── ティア設計(実装しない・user 裁定待ち)

> 🔴 **user 提起(2026-07-28)。本 doc の出発点**
>
> 「**SQLite を使うにしろ使わないにしろメモリにインデックスする分は常は少なくていい**はず、
> それは Postgres などの DB のアーキテクチャ的にも正しい。
> **実体化にかかる部分やソーティングのみに関わるインデックス**を持てばいい話のはず、と私は考えています。
> **DOM 再現についても、参照のみの場合は前回のレンダリング結果を使いまわせる**はず、
> つまり**ファストラインとして圧縮したレンダリング結果をストレージにキャッシング**して、
> キャッシュヒットに期待するのも十分にアリではないでしょうか?
> さらに**ユーザーのモニタや描画エリアサイズに適したレンダリングを行い低解像度キャッシング**するなどの方法もあるはず。
> つまり **PKC はティアレベルを持つ階層ストレージを必要とする段に入った**と考えるべき。
> **フォールバック経路を含めると複雑化する**が、**ストレージとキャッシュ層のアーキテクチャを固める必要がある**」

以降、この 4 つを **①常駐 index / ②描画キャッシュ / ③解像度適応 / ④ティア階層** と呼ぶ。

## 0. 先に測った ── 4 案の賞金はいくらか

設計を語る前に計器を置いた。**どれも「やってみないと分からない」ではなく数字が出る問いだった**ので、
先に測ってから設計している。新設した harness:

- `tests/bench/entry-meta-residency.mjs` ── entry メタ配列の常駐が N でどう伸びるか
- `tests/bench/center-render-repeat.mjs` ── 同じ entry を開き直したとき描画をやり直しているか

### 0-a. ①の賞金は**小さい**(が、棄却理由にはしない)

本文を空にした container を N だけ変えて seed し、強制 GC の後に JS heap を読む(2 回目起動・各 3 回の中央値):

| N | JS heap | サイドバー DOM 行 | nodes | listeners |
|---|---|---|---|---|
| 1,000 | 5.8 MB | 34 | 712 | 145 |
| 10,000 | 8.2 MB | 34 | 712 | 145 |
| 50,000 | 18.3 MB | 34 | 712 | 145 |

**傾き = 1 entry あたり 266 バイト**。10 万 entry でも**メタ配列は 25MB 程度**である。
P4b 後の body-heavy container の app 取り分が USS +164.7MB だったことと比べると、桁が 1 つ小さい。

⚠ **これを「効果が小さいからやらない」の根拠にはしない**(user 指示③)。ここで確定したのは
**「①のメモリ動機は弱い」**であって、①そのものの棄却ではない。①には**別の動機**があり得る
── 毎描画で全 N を sort / filter / tree 構築している **CPU 側**である。そちらは未計測なので
**計測タスクとして §9 に残す**。数字が出るまで①の優先度は決めない。

**副産物として重要な 2 つの事実**:
- **DOM 行 / nodes が N に依らず一定** ── S6(サイドバー窓化・既定 ON)が効いている
- **listeners が 145 で一定** ── ActionBinder が委譲(`data-pkc-action`)で張っているので、
  **描画結果を後から差し戻しても listener を張り直す必要がない**。②の実現可能性の前提が成立している

### 0-b. ②の前提は**成立する**。ただし②単独では 1/3 しか買えない

本文 120KB の text entry を 2 件作り、A↔B を交互に 5 往復して「選択 → center pane 描画完了」の
**long task**(メインスレッド占有)を測った:

| | wall | long task |
|---|---|---|
| 初回 2 回の平均 | 2,076 ms | **1,915 ms** |
| 3 往復目以降の平均 | 2,243 ms | **2,061 ms** |

**同じ entry を開き直しても速くならない ── 再利用が 1 ミリも効いていない。**
user の見立て「参照のみの場合は前回のレンダリング結果を使いまわせるはず」は**そのとおり**で、
今は毎回まるごと描き直している。

そこで「キャッシュが当たったら何秒で済むのか」の**下限**を測った。描画済み HTML を取り出し、
gzip → 展開 → `innerHTML` で作り直す時間:

| | 値 |
|---|---|
| 生 HTML | 1,544 KB(**21,416 要素**) |
| gzip 後 | **56.6 KB**(原文 120KB の 47%) |
| gzip 圧縮 | 14 ms(保存側) |
| gzip 展開 | 5〜6 ms(読み出し側) |
| `innerHTML` で再構築 | **1,291〜1,447 ms** |

**キャッシュヒットの下限 ≒ 展開 6ms + 再構築 1,291ms = 約 1,300 ms。**
現行の約 2,000 ms に対して **買えるのは 700ms 程度(約 35%)** にすぎない。

🔴 **理由: 支配的なのは markdown → HTML の変換ではなく、HTML → DOM の構築である。**
120KB の本文が **21,416 要素**になり、その構築だけで 1.3 秒かかる。
キャッシュは変換を消すが、**要素を作る仕事は消さない**。

### 0-c. ④と組ませると桁が変わる ── **ここが本 doc の核心**

同じ HTML を「先頭から一部だけ」流し込んだときの時間(ブロック境界で切り、部分木の要素数で割った):

| 挿入量 | ブロック | 要素 | `innerHTML` |
|---|---|---|---|
| 10% | 38 | 2,131 | **128 ms** |
| 25% | 94 | 5,267 | 339 ms |
| 50% | 188 | 10,531 | 613 ms |
| 100% | 375 | 21,416 | 1,291 ms |

**きれいに線形**(約 60 µs / 要素)。つまり center pane も**サイドバーと同じ理屈で窓化できる**。

4 つの経路を並べると:

| 経路 | 見積り | 現行比 |
|---|---|---|
| 現行(毎回まるごと描き直し) | ~2,000 ms | — |
| ②のみ(全量キャッシュ + 全量差し戻し) | ~1,300 ms | −35% |
| ④のみ(窓化・変換は毎回) | 変換 ~700ms + 挿入 128ms ≒ **~830 ms** | −59% |
| **②+④(ブロック単位キャッシュ + 窓化)** | 展開 6ms + 挿入 128ms ≒ **~135 ms** | **−93%** |

🔑 **②と④は掛け算になる。どちらか片方では足りない。**
そして**順序がある** ── ④(窓化)を先にやると単独で −59% が入り、その上に②を載せると −93% になる。
逆順(②を先)だと −35% で止まり、しかも次の④で作った資産の作り直しになる。

🔴 **この事実は設計に 1 つ硬い制約を課す。キャッシュは「1 本の HTML 文字列」で持ってはいけない。**
窓化して一部だけ差し込むには**ブロック単位で取り出せる**必要があり、
1 本の文字列だと切り出すために全部 parse する羽目になって**挿入と同じ額を払う**(= ②のみの経路に落ちる)。
**キャッシュの単位はブロックであり、ブロックごとの長さ(spacer 用の高さ)を併せ持つ。**
これはサイドバー窓化(L3-S3〜S5)で `data-pkc-row-count` + spacer が果たした役割と同型である。

### 0-d. 🔴 その前に ── **P4a / P4b は既定の user に 1 バイトも届いていない**

設計案の敵対的検証(3 案 × 4 レンズ)が出してきた指摘を、**自分で実機確認した**。

`mountBodyWorkingSet` は `bodiesDeferred === true` のときだけ呼ばれ(`main.ts:1310`)、
`bodiesDeferred = (__pkc_layout__ >= 2)`(`idb-store.ts:1403`)である。
そして layout ≥ 2 を書くのは**退役した `lazy_entry_bodies`** だけ。
既定 user の record は `__pkc_layout__ === undefined` なので **false** になる。

実測(本文 20,000 字 × 500 件 = 1,000 万字。上限 200 万字を 5 倍超過):

| 起動 | body working set | storage record |
|---|---|---|
| **既定(flag なし = IDB inline)** | 🔴 **mount されない** | `__pkc_layout__=null` / `entries[0].body` = 20,005 字が inline |
| `storage.sqlite_backend=true` | ✅ mount される | 同上(移行前) |

⇒ **P4b(本文 LRU 追い出し)も P4a(revisions の要求時読み)も、
`storage.sqlite_backend` を自分で ON にした人にしか効いていない。**
先の PR で報告した「app 取り分 451MB → 165MB(−63%)」は
**sqlite backend 上の数字**であり、既定の user が今日得ているものではない。

さらに言えば、user 指示④「container 丸ごと 1 JSON record への反対」は
**今日の既定そのもの**である ── `reassembleSplit` は marker が無い record を
そのまま Container として返す(`idb-store.ts:1222`)ので、
boot で entries(本文込み)+ relations + revisions(snapshot 込み)が全量 heap に載る。

**この事実が本 doc の段階順を決める**(§7):
- **描画レーン(C2〜C4)は backend に依存しない** ── 今日の既定 user にそのまま効く
- **storage レーン(ティア T2 等)は「既定 backend をどうするか」の裁定が先** ──
  それが決まらないうちは、どんな層を積んでも既定 user には届かない

### 0-e. 幸い、ブロック境界の機構は**既にある**

`src/features/ast/render-html.ts` の `renderAstToHtml()` は AST のブロックを 1 個ずつ HTML 化して
join しているだけで、`sourceLineAnchors` を有効にすると各ブロックに
`data-pkc-source-line` が付く(`render-html.ts:68`、Split View preview が既に使っている)。
**join する前の配列を返せるようにする**のが②+④の入口であり、新機構ではない。

## 1. ティア定義

「所有者・寿命・破棄条件」を持たない常駐物を作らない。**これは B13 / B18 / B9 / B12 で実際に踏んだ
事故がすべて「所有者と寿命が無かった」型だったことによる。**

| ティア | 媒体 | 中身 | 所有者 | 寿命 / 破棄条件 | 目安サイズ |
|---|---|---|---|---|---|
| **T0 hot** | JS heap + DOM | 可視ブロックの DOM / サイドバー窓の行 / 選択中 entry の本文 | renderer | 窓が動いた瞬間・選択が変わった瞬間 | 窓ぶん(N 非依存) |
| **T1 warm** | JS heap(上限つき LRU) | 本文 working set(P4b、200 万文字)/ 直近 entry の**ブロック HTML 配列** | working set | 上限超過で古い順・選択/編集中は対象外 | 上限で決まる |
| **T2 durable** | sqlite 行 / OPFS / IDB | core record の行 + **render cache 表(ブロック単位・gzip)** + asset Blob + 低解像度ラスタ | storage adapter | **quota 逼迫時に cache から先に捨てる**。core より先 | cache は本文の約 50%(実測 47%) |
| **T3 cold** | 交換形式 | export ZIP / pkc-data 埋め込み | user 操作 | user が消すまで | — |

**T2 の cache は「捨てられること」が設計要件**である。捨てて困るものを入れてはならない
── 入れた瞬間にそれは cache ではなく正本になり、⑦(双方向互換)と S1〜S4(静かなデータ喪失)の
両方に穴が開く。

## 2. 常駐集合の定義(①への回答)

**T0 + T1 に載ってよいものの閉じたリスト**:

1. 選択中 entry の本文(1 件)
2. 直近に見た本文(上限 200 万文字の LRU。P4b で実装済み)
3. サイドバーの窓に入っている行のメタ(S6 で実装済み)
4. 直近に見た entry のブロック HTML 配列(**新規・上限つき**)
5. 並べ替え / 絞り込みに必要な列

**5 が①の核心**であり、ここだけが未決である。現状は `AppState.container` に**全件のメタが載っている**
(`app-state.ts:105` の `container: Container | null`)。これは **Invariant 4「Container is source of
truth」**の直接の帰結であって、バグではなく設計である。

user 提案の「実体化とソートに要るぶんだけ」を厳密にやるなら、並べ替えは SQL 側
(`ORDER BY … LIMIT … OFFSET`。索引は B3 で 6 本入れてある)に降ろし、heap には窓ぶんしか置かない。
**それは Invariant 4 の再解釈を要求する** ── §10 の裁定事項 1。

⚠ ただし §0-a のとおり**メモリ動機は 10 万 entry で 25MB** と弱い。
やるなら動機は CPU(毎描画の O(N))であるべきで、**その数字はまだ無い**。

## 3. レンダリングキャッシュ(②への回答)

### 3-a. 効く対象と効かない対象を分ける

| 対象 | キャッシュ | 理由 |
|---|---|---|
| text / textlog の markdown 本文 | ✅ **主戦場** | 出力が (body, flags, theme, markup 版) の関数。実測 −93% の余地 |
| todo / form / folder の body | △ 小さい | 元々ブロック数が少なく、賞金が無い |
| spreadsheet | ❌ **除外** | 🔴 view wrapper に**直付け listener**(`spreadsheet-presenter.ts:1975`)。HTML を差し戻すと **export / embed ボタンが無言で死ぬ**。委譲へ移す小 PR を先に着地させない限り対象にしない |
| mermaid / chart | ③ の領域 | SVG / canvas は HTML キャッシュではなく**ラスタ**で扱う(§4) |
| 添付プレビュー / 画像 | ③ の領域 | Blob と ObjectURL の所有権が絡む。HTML には入れない |

### 3-b. キー

`(container_id, lid, body_hash, markup_version, flags_digest, theme)`

🔴 **鍵は「入力」で作る。出力(HTML)のハッシュを使ってはならない。**
`renderMarkdown` は純関数に見えて**非決定的**である ── `markdown-render.ts:250` と
`html-sandbox.ts:53` が `Math.random()` で id を生成しており、
**同じ入力から 2 回描いても HTML は一致しない**。出力ハッシュを鍵にすると常に miss し、
素朴な DOM 突合(「キャッシュが正しいか比べる」型の test)は**偽陽性を出す**。

- `body_hash` ── 本文が 1 文字でも変われば別物。**内容ハッシュであり updated_at ではない**。
  ⚠ 時刻を鮮度印にできないことは実コードで確定している ──
  `app-state.ts:1388` は `meta.entry_order` を書き換えるのに `updated_at` を bump していない
  (`snapshotEntryOrder` 経路も同様)。**しかも bump 漏れしているのは #1022 で実際に消えた
  `entry_order` そのもの**である
- `markup_version` ── markdown 方言のビルド識別子。**ビルドが変わったら全無効化**。
  これが無いと、新しい記法を足したビルドで古い HTML が当たり続ける
- `flags_digest` / `theme` ── 描画に効く flag(見出し番号・折りたたみ等)と配色

### 3-c. 保存形

**ブロックの配列**で持つ(§0-c の制約)。1 ブロック = `{ index, html, srcLine, heightHint }`。
`heightHint` は spacer 用で、サイドバー窓化の `measureUnitRowHeight` と同じ役割
── ただし本文ブロックは**高さが一様でない**ので、行高の中央値では代用できない。
**実測した高さをブロックごとに記録し、未測定は保守的な推定値**にする(サイドバーより難しい点)。

⚠ `content-visibility: auto` の未表示要素は**嘘の高さを返す**(サイドバーで実測 39px vs 真値 24.91px)。
高さの記録はこの罠を踏む位置にあるので、**測る対象は必ず「今 viewport に入っているブロック」**にする。

### 3-d. 置き場所 ── **別 DB `pkc2-derived`**(初稿から訂正)

初稿では「専用の object store」と書いたが、**これは誤りだった**。敵対的検証が実コードで反証した:

```
idb-adapter.ts:25   const DB_VERSION = 3;
idb-adapter.ts:35   const req = indexedDB.open(DB_NAME, DB_VERSION);
idb-adapter.ts:112  req.onerror = () => reject(req.error);   ← VersionError の分岐が無い
```

`pkc2` に store を足すには DB_VERSION を 4 に上げる必要があり、そうすると
**`open('pkc2', 3)` の旧 `pkc2.html` は VersionError で DB ごと開けず起動不能**になる。
#1022(relations が 0 件に見える)より重い ── **アプリが起動しない**。

⚠ この壊れ方は**今日この目で見た** ── smoke spec が `indexedDB.open('pkc2', 2)` と
version をべた書きしていたせいで、53 test が `VersionError` で一律に死んでいた(本日の hotfix)。

`containers` store への相乗りも駄目である。`listContainers`(`idb-store.ts:1586-1600`)は
**既知 prefix の除外リスト方式で、残り全 key を `get` する**。相乗りすると旧ビルドは
**container switcher を開くだけでキャッシュを全読み**する(コメント自身が過去の性能退行として警告している)。

⇒ **別 DB `pkc2-derived`(version 1 固定)**に置く。
前例あり: `fsa-handle-store.ts:15` が**まったく同じ理由**で `pkc2-fsa`(DB_VERSION=1)を切っている。
sqlite backend のときは専用表でよい(同一 DB 内でも旧ビルドは sqlite を読まないため露出しない)。

## 4. 解像度適応(③への回答)

対象は**ラスタ化できるもの**に限る:

| 対象 | 今 | 提案 |
|---|---|---|
| 画像添付 | 原寸 Blob → CSS で縮小 | 表示領域 × devicePixelRatio のサムネイルを T2 に持つ |
| contact sheet / book-base のサムネ | 同上 | 同上(一覧は特に効く) |
| mermaid | SVG を DOM に展開(**1 枚で renderer +6.9MB** の実測) | 表示サイズでラスタ化して T2 に置き、SVG は捨てる |
| chart.js | canvas | 静止時はラスタ、操作時に再生成 |
| markdown 本文 | — | **対象外**(テキストは解像度非依存) |

✅ **裁定済み(user 2026-07-28)**: 「**mermaid に関してはラスタ表示と複数種コピーで
分ければいい**」──「ラスタ化するとテキストが選べなくなる」という懸念は、
**表示はラスタ / 取り出しはコピー**と役割を分ければ解消する、という整理。
よって既定でラスタ化してよい。

⚠ ただし **複数種別コピーは user が別途要望する予定**(同日)。本 doc の範囲では
**作らない**(プライム・ディレクティブ「機能を足さない」)。
C6 は**表示のラスタ化まで**とし、コピー側は user の要望が来てから別レーンで扱う。
拡大・ウィンドウリサイズでの再生成経路は C6 に含める。

## 5. フォールバック(user 提起④「フォールバック経路を含めると複雑化する」)

**複雑化の大半は「キャッシュが無かったらどうするか」ではなく「キャッシュがあるのに信じてよいか」である。**
前者は 1 経路(素直に描く)で済み、後者が分岐を生む。だから**キャッシュを一切信用しない既定**を作る:

| 事象 | 挙動 |
|---|---|
| ミス | 通常描画。**常に成立する**(キャッシュは純粋な派生物) |
| 復号 / parse 失敗 | 破棄して通常描画。⚠ **例外を握って黙らせない** ── `?pkc-debug=render-cache` で可視化 |
| キー不一致(ビルド更新・flag 変更) | ミスと同じ |
| quota 超過 | **T2 の cache から先に捨てる**。core record より必ず先 |
| **blob URL の失効** | 🔴 `cleanupBlobUrls`(`action-binder.ts:11250`)が **render のたびに `data-pkc-blob-url` を全部 revoke** する。キャッシュした HTML に `blob:` を焼き込むと、差し戻した瞬間に**死んだ URL** になる。⇒ **キャッシュには `asset_key` を残し、差し戻し後に registry から引き直す**。`data:` base64 の焼き込み(`asset-resolver.ts`)も同じ理由で対象外にする |
| **ブラウザによる無言の退避** | 🔴 `navigator.storage.persist()` は **repo 全体で 1 度も呼ばれていない**(`estimate()` と `getDirectory()` のみ)。したがって storage は best-effort で、退避単位は **DB ではなく origin** ── **アプリに通知は来ない**(次回起動で消えている)。「派生から先に捨てる」は**アプリが退避順を制御できる前提**だが、その前提は今日成立していない。⇒ T2 の cap を厳しく張り、**`persist()` を呼ぶかを裁定事項に上げる**(§10-6) |
| OPFS 不可 | 既存 `storage-adapter` の seam で IDB へ。cache も同じ経路に乗る |
| readonly container | T2 に書かない(T1 のみ) |
| embed(iframe) | T2 を使わない |
| 旧ビルド | cache 表を知らない。**core record に混ざっていないので何も見えない**(§6) |

## 6. 双方向互換の判定表(Invariant 5)

**「この変更を知らない読み手が core record だけを読んだら何が見えるか」**:

| 読み手 | 見えるもの | 判定 |
|---|---|---|
| 新ビルド → 旧データ | cache が無いだけ。全部読める | ✅ |
| **旧ビルド → 新データ(core record)** | **今日とまったく同じ**。cache は別 store / 別表にあり core に 1 バイトも混ざらない | ✅ |
| 旧ビルドが store を列挙 | **cache を別 object store に置く限り見えない**。⚠ 同じ store に別キーで置くと幽霊 container として出る(#1022 と同型) | 設計制約 |
| 旧ビルドが保存 | cache を消すかもしれない。**消えても正しい**(派生物) | ✅ |
| 交換形式(export ZIP / pkc-data) | cache を**含めない**。派生物を交換形式に入れない | ✅ |

## 7. 段階 ── **影響の少ない順かつ効果の高い順**(user 指示 2026-07-28)

> 「まずは**影響の少ない順かつ効果の高い順**で実装しましょう」(user 2026-07-28)

**影響** = user に見える挙動 / データ形式 / 不変条件をどれだけ動かすか。
**効果** = 実測で分かっている賞金。両方を書き、**影響が小さく効果が大きいものから**積む。

🔴 **描画レーンが先**である。§0-d のとおり storage レーンは
「既定 backend をどうするか」の裁定が済むまで**既定 user に 1 バイトも届かない**が、
描画レーンは backend に依存せず**今日の既定 user にそのまま効く**。

| 順 | 段階 | 内容 | 影響 | 効果(実測) |
|---|---|---|---|---|
| ✅ | **P0** | todo の未読ガード(§12-1)。**着地済み** | 小(既定経路は挙動不変 ── 未読が無ければ同期のまま) | データ喪失窓を塞ぐ |
| 1 | **C1** | 計器: center pane の long task / ブロック数 /(後に)hit 率 | **ゼロ**(計測のみ) | 0 ── 以降すべての前提 |
| 2 | **C2** | `renderAstToHtml` を**ブロック配列**で返せるようにする(join を呼び出し側へ) | **ゼロ**(出力 HTML は 1 バイトも変わらない前工事) | 0 ── L3-S2 と同じ性格。C3 を断念しても資産が残る |
| 3 | **C3** | **center pane のブロック窓化** | 中(描画の出方が変わる。ただし L3-S5 で同型を着地済み) | **−59%**(2,000 → ~830 ms) |
| 4 | **C4** | ブロック単位 render cache を **T1(メモリ)** に | 小(メモリ内のみ。捨てても正しい) | **合計 −93%**(~135 ms) |
| 5 | **C6** | ③ 解像度適応ラスタ(mermaid / 画像 / contact sheet) | 中(見た目が変わる ── ただし裁定済み) | mermaid 1 枚 −6.9MB |
| 6 | **C5** | cache を **T2(永続)** へ | **大**(quota / 破損 / 旧ビルド / 別 DB のフォールバックが増える) | **未計測**(§9) |
| 7 | **C7** | ① 常駐 index の縮小 | **大**(Invariant 4 の再解釈) | **未計測**(§9 の CPU 内訳しだい) |

**C2+C3 だけで現行の 6 割が消える**。しかも C1・C2 は影響ゼロなので、
**最初の 2 段は裁定を待たずに積める**。

⚠ 順 6・7(C5 / C7)は user 指示により保留 ── §10 冒頭。

## 8. 採らないもの

- **center pane 全体を 1 本の HTML としてキャッシュする** ── 採らない。§0-c の実測で
  **−35% で頭打ち**になり、しかもブロック窓化と両立しない形になる。方向ごと否定される案
- **キャッシュを core record に同居させる** ── 採らない。⑦ に触れる(#1022 と同型)
- **markdown 本文の低解像度化** ── 採らない。テキストは解像度非依存で、意味がない

⚠ **「効果が小さい」を理由に落としたものは 1 つも無い**(user 指示③)。
効果が不明なものは §9 の計測タスクに送っている。

## 10-b. 旧・裁定が要る点(全文)

1. 🔴 **Invariant 4 の再解釈**(①の前提)。
   現在「Container is source of truth」= 全件メタが heap に常駐。
   これを「**storage が正本、heap は窓**」へ変えるか。

6. 🔴 **既定 backend をどうするか**(§0-d で判明した最重要点)。

## 12. 検証で出た**既存の欠陥**(本設計とは独立。別 hotfix)

設計案の敵対的検証(3 案 × 4 レンズ = 12 経路、うち 12 が refuted)は、
案の欠陥だけでなく**今日そこにある欠陥**を 3 件掘り出した。いずれも自分で実コードを確認した。

### 12-1. 🔴 todo の read-modify-write が未読の本文を掴む窓

`parseTodoBody('')` は `JSON.parse('')` が throw → catch → `{ status:'open', description:'' }`
(`todo-body.ts:36-38`)。`serializeTodoBody` は falsy なキーを書かない(`:42-51`)。
⇒ **未読(`body === ''`)の todo を read-modify-write すると、期日・アーカイブ・説明文が消える。**

この read-modify-write を行う経路は 5 箇所あり、**どれも未読ガードが無い**:

| 経路 | 位置 |
|---|---|
| `toggle-todo-status` | `action-binder.ts:2829` |
| `handleKanbanDrop` | `action-binder.ts:7527` |
| `handleCalendarDrop` | `action-binder.ts:7629` |
| `BULK_SET_STATUS` | `app-state.ts:3932`(**reducer 内 = 非同期 hydrate できない**) |
| `BULK_SET_DATE` | `app-state.ts:3955` |

未読ガード(`isBodyPendingGlobal`)は保存経路にはあるが(`idb-store.ts` / `sqlite-store.ts`)、
**この 5 経路からは 1 度も呼ばれていない**。

**窓が実在することは実機で確認した**(sqlite backend ON / 本文 4KB × todo 300 件):
**boot 直後に未読が 236 件**(常駐 261,046 字)。つまり 236 件の todo が
`body === ''` のまま state に載っている。

**今日 user に届いていない理由は「安全だから」ではない** ── §0-d のとおり
**既定では body working set が mount されないので未読が発生しない**だけである。
`storage.sqlite_backend` を ON にした環境では窓が開いている。

⚠ これは #1028(「読めなかった本文を空の本文として確定させない」)と**同型**で、
あのときは `save()` 側だけを塞いだ。**同じ穴が todo の書込経路に残っていた。**

### 12-2. `navigator.storage.persist()` が 1 度も呼ばれていない

`src/` 全体で `navigator.storage` の使用は `estimate()` と `getDirectory()` のみ。
storage は best-effort のままで、ブラウザの退避は **origin 単位・無通知**である。
派生層の設計とは独立に、**今日のデータ耐久性の話**として扱うべき(§10-7)。

### 12-3. `updated_at` が鮮度印として使えない

`app-state.ts:1388` は `meta.entry_order` を書き換えるのに `updated_at` を bump していない
(`snapshotEntryOrder` 経路も同様)。**bump 漏れしているのは #1022 で実際に消えた
`entry_order` そのもの**である。派生層の鮮度判定に時刻を使う設計は成立しない(§3-b)。

## 13. user が別途予定している変更(設計上の留意)

本 doc の実装が**前提にしてはいけない**もの。いずれも user から 2026-07-28 に通告。

### 13-1. 大きなテーブルの描画を「ある程度で打ち切る / 別画面閲覧」にする

> 「**大きなテーブルオブジェクトの描画もある程度で打ち切るか別画面閲覧にするつもりでした**」

C3(center pane のブロック窓化)と**同じ問題への別解**であり、**競合しない ── 補完する**。
120KB の本文が 21,416 要素になる内訳のうち、表は 1 ブロックで
`table > thead/tbody > tr > th/td` と要素数を稼ぐ**最も重いブロック種**である。

⇒ C3 の窓化は**ブロック単位**なので、「1 個の巨大な表」は 1 ブロックのまま残り、
窓化だけでは分割できない。**表の打ち切り / 別画面は C3 の穴を塞ぐ**位置にある。
設計上は「ブロック 1 個が極端に重い場合の扱い」を C3 の非目標として明記し、
user の変更に委ねる。

### 13-2. コードブロックのフェンスを機能改修する

> 「**コードブロックのフェンスについては、機能改修するので、そこら辺は留意だけお願いします**」

🔴 **render cache のキーに直結する。** §3-b の `markup_version` は
「markdown 方言のビルド識別子」であり、**フェンスの解釈が変わったら
既存のキャッシュは全部無効化されなければならない**。さもないと
**改修前の HTML が改修後のビルドで当たり続ける**。

⇒ C4 を実装するときの不変条件:
- `markup_version` は**フェンスの実装を含む markdown 経路のダイジェスト**から作る
  (手で上げる定数にしない ── 上げ忘れが必ず起きる)
- 改修中は cache を **flag で丸ごと切れる**ようにしておく
